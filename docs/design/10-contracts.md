## Engine: events in, effects out

`apply(def, snapshot, event, now)` is pure. Ids (`command_id`, `input_request_id`) and `event.id` are assigned by the EngineService wrapper, which writes the event rows, the session row and the outbox rows in one transaction, then publishes the board events to the BoardBus (or returns them in `boardEvents` for a caller-owned `tx` to publish after its COMMIT).

## EngineService wrapper

Writes `apply()` can't make (it has no ids and doesn't see these columns), all in the apply transaction (T04):

- Assigns `command_id` / `input_request_id`. For a `start_session` effect it also sets `session.agent_command_id` = that `command_id` and `agent_process_live = false`.
- Builds each outbox row with `commandPayloadForEffect(effect, {command_id, snapshot, branch: session.branch})`: `outbox.kind`, `target`, `payload` (the WS payload verbatim) and `outbox.fencing_token` = the session's token after this apply ([Effect → WS](#effect--ws-fields)). It never renders or rewrites a prompt ([Prompt render](#prompt-render)).
- On a non-ignored `session.started`: `UPDATE session SET worktree_path, branch, port_range = int4range(base, base+count)` (`[base, base+count)`). The gateway does **not** write these.
- On `command.refused` for `start_session` that apply did **not** ignore: `session.fencing_token = nextval('fencing_seq')`, so events from a process that command spawned anyway are stale ([Orphaned processes](#orphaned-processes)). An ignored refusal (U-025 rule) bumps nothing.
- **Gate-step fencing** ([ADR-0010](../adr/0010-one-workflow-columns-are-states.md), security review 2026-10-23): when apply enters, leaves or switches a gate step (`step` null ↔ set, or a different step label), the token is bumped the same way. The worker (between its `complete_state` and its exit) and a finished reviewer run under the old token, so none of their events can reach the step or the next visit: the gateway refuses them `stale_fencing_token` and kills the process. The one exception is `spend`: a fenced-off process's last `spend` from the session's machine is still applied (cumulative per Claude session, it never moves the ticket), without a kill. The ADR-0009 path on `main` had the same gap (worker and reviewer shared a token) and is fixed by the same bump.
- **Terminal fencing** (BUG-1): when apply moves the session from a non-terminal status to `done`, `failed` or `lost`, the token is bumped the same way, so any process still running for the session is stale ([Orphaned processes](#orphaned-processes) rule 6). The outbox rows of that apply (e.g. its `kill`) carry the new token. M2-T20 owns the full list of fencing triggers.
- On `input.provided`: checks the `input_request` is open, records `answer`, `answered_by` (= `opts.actor`), `answered_at`, and writes the `input.answered` board row.
- On an applied `human.transition` ([ADR-0011](../adr/0011-transition-rules.md)): answers the session's open `input_request` (answer = `text` ?? `"[<name>]"`, `answered_by` = the event's `actor`) and writes its `input.answered` row. Nothing on an ignored one.
- On an applied `gate.retry`: answers the open `check_config` request (answer `[$retry_checks]`, `answered_by` = the event's `actor`).
- On an applied `agent.ask_user` with `proposed_checks`: after inserting the `input_request`, stores the proposal (`createProposal`, linked by `ticket_id` / `input_request_id`, `created_by: agent:<ticket>`) in the same transaction; a refusal is appended to the request's question.
- ADR-0037 P1 (T6): when a `watch.fired` or `action.completed` moves a session out of the human state it was parked in (a watch's `on_broken`), the open `input_request` is answered `[the watch moved the ticket]` by `system`, before the landing opens its own. `session.watch_deadline` is written from the snapshot like the other columns (the watch's checklist rides in `context.__watch`, its way back in `context.__watch_return`). After the session row, a nudging event (above) brings the same repo's watches forward. ADR-0037 P4 (T7): a `timer.fired` for a session whose step is `held` becomes `concurrency.checked` before apply (above). A `hold_changed` effect writes an event row `concurrency.held` (`{state, behind, since}`) or `concurrency.released` (`{state, behind, since, cause, held_ms}`); never a push. After the session row, a session that left a real state or ended (or a watch-nudging event) sets `state_deadline = now` on the same repo's held moves.
- On an applied `human.fresh_conversation` ([Fresh conversation](#fresh-conversation)): answers the open `input_request` the same way (answer = `text`, `answered_by` = `actor`) and bumps `session.fencing_token` (`nextval('fencing_seq')`), so the replaced process (killed by apply, or one that comes back late) is stale.
- `state_entered` → the `state.entered` event row's payload `StateEnteredPayload` `{from, to, visit, transition?, reason?, actor?}` (the ADR-0011 fields only when apply set them; `toMoveDto` reads absent as null). `actor` is `MoveActorSchema` (`agent | human | system | engine`). Every route conductor takes on its own records why, with actor `engine` and a one-line `reason` (≤ 300 chars): `ENGINE_MOVE` names `requirements_unmet` (a gate's checks or review items not met, back to `on_unmet.goto`; reason = the unmet items), `requirements_unmet_exhausted` (to `on_unmet.else`), `step_failed` (a gate step that could not finish), `fallback` (no route: the fallback human state), `retries_exhausted` (a counted loop's `else`), `budget_exceeded`, `machine_lost`; and the engine outcomes `timeout`, `fail`, `error` under their own names. An answer (`input.provided`) records actor `human` with a null `transition` and the answer as `reason`. A start or requeue records nothing; an unnamed agent outcome keeps the M1 record. `isNamedMove(m)` (transition set, actor not `engine`) is what the board treats as a transition someone took (`InputRequestDto.origin_transition` is null for an engine route; `engine/rows.ts` reads the origin's `actor`).
- `state_entered` with `notify` (a transition with `notify: true`, [05 §Notify](05-workflow-engine.md#notify)) → renders `transitionPayload` (below, [Web Push](#web-push)) from the pinned definition (the transition's title, the source state's column title, or the step's `from` when `from` is a gate-step label, and the target's title). With push enabled it enqueues `push_transition` rows (`enqueueTransitionPush`), and it always writes a `transition.notified` board row **after** `card.upserted`, so the card it names is current.
- `conversation_reset` → a `conversation.reset` event row, payload `ConversationResetPayload` `{claude_session_id, reason}` (the forgotten conversation; `reason` `not_on_machine` from a [refusal](#refusals), `user_requested` from a [fresh conversation](#fresh-conversation)). Audit only: no board event.
- After the effects: writes a `card.moved {from, to}` row when the card's column changed, then one `card.upserted` row (last) if any `BoardCard` field changed (status, column, badges, `checking`, `pr_url`, `workflow_state`, `machine_id`, `spend_usd`, open input request, `updated_at` on any change). The card is `toBoardCard(ticket, session, openInput, view)`, `view` = `{columns: boardColumns(<latest conductor>), def: <the session's pinned definition>}` (`orchestrator/src/engine/board-view.ts`; the column rule is `placeCard`, [06](06-human-input.md#kanban-columns-the-workflows-states)). It carries the open input request only while the session is `needs_input`: a cancel leaves the row unanswered, but the card drops it (TD-079).
- Writes every board row through `insertBoardEvents(tx, drafts)`, as the last write of the transaction.

## Board events and the event table

**One writer path.** T04, T08 and T11 write board rows only through `insertBoardEvents(tx, drafts)` (`orchestrator/src/contracts.ts`). It takes `pg_advisory_xact_lock(BOARD_EVENT_LOCK_KEY)` before the first INSERT and holds it to COMMIT, so board-writing transactions commit in `event.id` order and a `Last-Event-ID` replay (`id > $1`) can't skip a lower id that commits later. Call it last in the transaction to keep the lock short; publish the returned events after COMMIT. Engine audit rows don't take the lock (they are never replayed).

Every `BoardSseEvent` is backed by **exactly one** `event` row: `type` = the SSE `type`, `session_id` = the SSE `session_id`, `payload` = the SSE event minus `{type, id, ts, session_id}`, and the row's `id`/`ts` are the SSE `id`/`ts`. Writers build rows with `boardSseEventToRow(draft)` and decode `INSERT … RETURNING *` with `boardSseEventFromRow(row)`, which T08 also uses for `Last-Event-ID` replay (`WHERE id > $1 AND type = ANY(BOARD_SSE_EVENT_TYPES) ORDER BY id`); it returns null for non-board rows. Engine-event rows (`type` = `EngineEvent.type`) and `state.entered` are audit rows, never replayed to the board.

| SSE event | Written by | When |
|---|---|---|
| `card.upserted` (`session_id` null for a sessionless ticket) | T08 (with the ticket INSERT, same tx); T04 wrapper (see above, incl. the claim's `session.assigned`) | new ticket; any card change |
| `card.moved` | T04 wrapper; reopen | the card's column (`placeCard`) changed; `from` / `to` are column ids ([ADR-0010](../adr/0010-one-workflow-columns-are-states.md)) |
| `session.status` | T04 wrapper | `session_status` effect |
| `input.requested` | T04 wrapper | `create_input_request` effect |
| `input.answered` | T04 wrapper | `input.provided` applied |
| `card.badge` | T11 gateway, its own tx | `session_event build_slot` |
| `transition.notified` `{ticket_id, from, to, transition, title, body, tag}` | T04 wrapper (last) | `state_entered.notify`: a transition with `notify: true` was taken. `title` / `body` / `tag` = the push's |

The client keeps one card per `ticket_id`; `card.upserted` replaces it wholesale. New cards appear only via `card.upserted`, so `card.moved.from` is never null.

## Claim

T11, one transaction ([04](04-scheduler.md#2--claim-query-ticket-side)). The partial unique index `session_one_live_per_ticket` ([02](02-data-model.md#session)) enforces step 2's "never a second session":

1. Claim query (`FOR UPDATE OF t SKIP LOCKED`); assign the ticket's agent ([below](#agent-assignment-ux-13a)); `UPDATE ticket SET status = 'claimed', agent_id`.
2. If the ticket already has a non-terminal session (a `queued` one left by a refused `start_session`), `UPDATE` it: new `fencing_token = nextval('fencing_seq')`, new lease. Otherwise `INSERT session` with `status = 'queued'`, `workflow_state = null`, `machine_id = null`, `agent_command_id = null`, `agent_process_live = false`, a new fencing token and lease, `branch = sessionBranch(ticket, session_id)`: `<KEY>-<slug>-<short>` when the ticket refers to a Jira issue, else `conductor/<slug>-<short>`. `<short>` = the first 6 characters of the session id (every session's branch is unique); `<slug>` = the title ASCII-folded, lower case, non-alphanumerics → `-`, at most 40 chars at a word boundary (`ticket` if empty). The Jira key (`[A-Z][A-Z0-9]{1,9}-<n>`) comes from, in order: `external_ref`, a Jira link (`/browse/KEY-1`, `selectedIssue=KEY-1`) in the title or body, a key in the title (not `NON_JIRA_KEY_PREFIXES`: `UTF-8`, `ADR-0031`…); a bare key in the body doesn't count. The result always passes `isSafeBranchName` (shared). It is fixed at claim: apply reads `snapshot.branch`, never recomputes it from an edited title, and a reopen carries it. Never a second session per ticket.
3. `applyEvent(session_id, {type: 'session.assigned', machine_id}, {tx})`: `queued → assigned`, `machine_id` set, `start_session` outbox row (its `branch` is read from `session.branch` by the dispatcher).
4. `COMMIT`, then publish the result's `boardEvents`, then reply `work_assignment`.

### Agent assignment (UX-13a)

`assignAgent` (`orchestrator/src/agents/team.ts`), in the claim's transaction, before `session.assigned` (so that event's `card.upserted` carries `agent_name`). The team is the **ticket's** account's ([02 §agent](02-data-model.md#agent)), whichever machine claims. A queued ticket holds no one.

1. **Keep.** The ticket already has an agent (`ticket.agent_id`, never cleared): keep it, so a retry, requeue or reopen keeps the same agent, even if it is busy elsewhere.
2. **Free teammate.** Else the teammate with no other active ticket (a session not `done` / `failed` / `lost`), oldest `last_assigned_at` first (never-assigned first), then oldest `hired_at`: `SELECT … FOR UPDATE OF a SKIP LOCKED`, so two claims never take one free teammate. Once the row is locked, the busy check runs again in a statement of its own (the locking statement's snapshot can predate the commit of the claim that held the lock); a busy one is skipped and the next tried.
3. **Hire.** Nobody free: insert an `agent` with the first name of `hireOrder(ticket_id)` not on the team. The order starts at `fnv1a('name:<ticket_id>') % AGENT_NAMES.length` (the name web derived before UX-13a) and walks forward, wrapping around. `ON CONFLICT (account_id, name) DO NOTHING`: a concurrent hire of the same name walks on to the next.
4. **Pool exhausted.** Every pool name is on the team and busy: reuse the teammate assigned longest ago, and log a warning.

Every path sets `last_assigned_at = now()`. Lock order: machine, ticket, agent.

**Reads.** Every ticket read that feeds `toBoardCard` uses `TICKET_SELECT` (`engine/rows.ts`: `ticket t LEFT JOIN agent a`), so every card, including each `card.upserted`, has `agent_name` (null = not assigned yet). `SessionDetail.agent_name` and `TicketDto.agent_name` are the same name; all three are optional on the wire (absent from older servers ≡ null). A new ticket's `POST /api/tickets` reply and card carry `agent_name: null`.

**`GET /api/team`** (`API_PATHS.team`, `orchestrator/src/api/team.ts`; signed in, 401 otherwise) → `TeamResponse`: the signed-in account's agents, oldest hire first, `[{name, hired_at, last_assigned_at | null, active_ticket_id | null}]`. `active_ticket_id` is the ticket of the agent's newest session that is not done, failed or lost. Another account's agents are never listed.

## Repo suggestions

**`GET /api/repos`** (`API_PATHS.repos`, `orchestrator/src/api/repos.ts`; signed in, 401 otherwise) → `RepoListResponse`, `[{repo, ticket_count, last_used_at | null}]`: the repos the create-ticket form offers, best first. ## Reopen

[ADR-0008](../adr/0008-transcript-history-and-reopen.md). `POST /api/sessions/:id/reopen {text}` → `reopenSession` (`orchestrator/src/engine/reopen.ts`), one transaction, no engine event and no outbox row:

## Daemon seq dedupe

`machine.last_seq` (bigint null) is the highest processed daemon `seq`. For every `session_event`, T11 opens a transaction, runs `UPDATE machine SET last_seq = $seq WHERE id = $machine AND (last_seq IS NULL OR last_seq < $seq)`, and on row count 0 (duplicate or replayed) skips the event. Otherwise it applies the event in the same transaction (`applyEvent(..., {tx, fencingToken})`, or the `build_slot` writes) and commits. `registered.last_seq` = `machine.last_seq` (as a number). A fencing rejection still commits the `last_seq` advance (the event was processed, by rejecting it).

**Daemon side (T05).** The daemon persists its last assigned `seq` locally. After every `registered`, the next `seq` it assigns is `max(local persisted seq + 1, registered.last_seq + 1)` (with `registered.last_seq = null` counting as -1). So a daemon whose local state was lost or is behind the orchestrator never reuses a `seq` the orchestrator has already seen (which would silently drop the event as a duplicate). It replays its buffered events with `seq > registered.last_seq`, in order, before new ones.

## Gateway details (T11)

Choices the gateway makes beyond the rules above ([03](03-protocols.md#daemon--orchestrator-websocket)):

- `register` upserts `machine` (`status = online`, facts, `claude_code_version`) and makes this machine's open outbox rows due now ([Outbox](#outbox-state-machine)); `registered.heartbeat_interval_ms` defaults to **10 s**. A second connection for the same machine id replaces the first (closed with 4000), and the replaced socket's close does not mark the machine offline.
- M2-T09 (gateway option `requireCredential`, default `CONDUCTOR_AUTH=password`): the upgrade's credential lookup also bumps `machine_credential.last_used_at`; a DB error there answers HTTP 503, which the daemon retries. In `password` mode `register` UPDATEs the row enrollment created (never its `name`); in `local` mode it keeps the M1 upsert (`account_id = LOCAL_ACCOUNT_ID`, `name = hostname` on insert). In both modes a machine with `revoked_at` set (or another account's id) is closed `CLOSE_UNAUTHORIZED`. `revokeMachine({db, sockets}, scope, id)` closes every connection of the machine, including one that authenticated but hasn't registered yet.
- A daemon socket close marks its machine `offline` (after its queued frames are handled).
- `heartbeat` stores `cpu_free` as `floor()` (int column), renews the leases of the sessions it lists under their current token on this machine, and kills those listed under a lower token ([Orphaned processes](#orphaned-processes) rule 4). A `session_event heartbeat` renews that session's lease.
- `command_ack` UPDATEs only the row with that `command_id` **and** `target = machine:<acking machine>`.
- The `superseded_start` kill (Orphaned processes rule 3) carries the session's current fencing token in its envelope.

## Outbox state machine

`pending → sent → acked | failed`. `acked` and `failed` are terminal. Status writes are partitioned and every UPDATE is guarded, so a fast ack can't be overwritten by the dispatcher. **Every UPDATE that makes a `start_session` row terminal also sets `payload.prompt` to JSON `null`** (`SCRUBBED_PAYLOAD_SQL`, `orchestrator/src/engine/outbox.ts`; other payload fields kept): the prompt can carry the `attach: output` tail, and a terminal row is never sent again (a requeue renders a new prompt from the session) ([U-039](../tracking/UNKNOWNS.md)). The same UPDATE nulls a `send_message` row's `payload.text` (up to 20 000 chars of human text; its record is the `operator.message` event row, [ADR-0007](../adr/0007-live-messages-to-agents.md)). `send_message` rows are retried like `send_input` (no ack timeout); the daemon dedupes them on `command_id`, so a message is written at most once.

| Who | Transition | Guarded UPDATE |
|---|---|---|
| T04 dispatcher | `pending`/`sent` → `sent` after `OutboxTransport.send` = `sent` | `SET status='sent', attempts=attempts+1, next_attempt_at=now()+backoff WHERE id=$1 AND status IN ('pending','sent')`; backoff after the n-th send 5, 10, 20, 40, then 60 s. `not_connected` changes nothing |
| T04 dispatcher | picks rows | `status IN ('pending','sent') AND next_attempt_at <= now()` for connected targets. Re-sending `sent` rows is safe (the daemon dedupes on `command_id` and re-acks) |
| T04 dispatcher | `sent` → `failed` (`start_session` ack timeout) | a `start_session` due again with `attempts >= 3` (≈ 35 s): `SET status='failed', last_error='ack_timeout' WHERE id=$1 AND status='sent'`; on row count 1 apply `command.refused {reason: 'ack_timeout'}` in the same tx. The command may still have reached the daemon: see [Orphaned processes](#orphaned-processes) |
| T11 gateway | → `acked` / `failed` on `command_ack` | `SET status = CASE WHEN $accepted THEN 'acked' ELSE 'failed' END, last_error = $reason WHERE command_id=$1 AND status IN ('pending','sent')`; a refusal with row count 1 applies `command.refused` in the same tx. Row count 0 = duplicate or late ack, ignored, **except** an `accepted=true` ack whose row is a `start_session` already `failed` and whose `command_id` is not `session.agent_command_id`: the gateway sends the orphan kill ([Orphaned processes](#orphaned-processes)) |
| T04 dispatcher | stale row → `failed` | a picked row with `fencing_token` < the session's current token is not sent: `SET status='failed', last_error='stale_fencing_token' WHERE id=$1 AND status IN ('pending','sent')`. No engine event (the token moved because the session was re-claimed or its start refused) |
| T11 gateway | on `register` | `SET next_attempt_at = now(), attempts = CASE WHEN kind = 'start_session' THEN LEAST(attempts, 2) ELSE attempts END WHERE target = 'machine:<id>' AND status IN ('pending','sent')` (status untouched) so commands are re-sent right after a reconnect, and a `start_session` always gets one more send (the ack timeout then fires ≥ 20 s after the reconnect, not at once) |

## Refusals

`command.refused {command_id, command_kind, reason}` replaces the earlier `session.start_refused`. apply routes it by `command_kind`:

- **U-025**: a `start_session` refusal is ignored (`command_id_mismatch`) unless `command_id == agent_command_id` **and** `agent_process_live = false`. A refusal for a superseded command, or one that arrives after its `started` (the process is up; only the ack was lost, then the ack timeout fired), changes nothing, and the wrapper doesn't bump the token.
- `start_session` → `status = queued`, `machine_id = null`, **`agent_command_id = null`, `agent_process_live = false`**, ticket `ready` (re-claimable; the claim reuses this session). The wrapper also bumps `session.fencing_token = nextval('fencing_seq')` in the same tx. A refused or timed-out `start_session` may still have spawned a process (late ack); the null `agent_command_id` makes apply ignore its `started`/`exit`, and the bumped token makes every other event from it stale. See [Orphaned processes](#orphaned-processes).
- **`no_conversation`** (`NO_CONVERSATION_REASON`, a `start_session` refusal): the start asked to resume a Claude conversation whose transcript is not on the claiming machine (it ran on another one; `claude --resume` would exit 1 with "No conversation found"). The daemon checks before spawning (`hasTranscriptInCwd`: `<config dir>/projects/<slug of the worktree's realpath>/<id>.jsonl` exists, the only place `claude --resume` looks; not `findTranscript`'s any-project-dir fallback, which history and reopen keep using; for `resume_claude_session_id` of a worker or a reviewer) and refuses without starting anything, releasing the slot. apply handles it as any `start_session` refusal (requeue, above) and also forgets the conversation: `claude_session_id = null` (in a review step, the reviewer's `review.claude_session_id`, never the worker's), plus a `conversation_reset {claude_session_id: <old>, reason: 'not_on_machine'}` effect (event row `conversation.reset`). `pending_answer` is kept, so the re-claim's `start_session` has `resume_claude_session_id: null` and the full rendered state prompt with the answer in it ([Pending answer](#pending-answer)). The agent loses the earlier conversation's context but not the worktree (if the claiming machine has the branch) or the answer. After the commit the gateway appends a `debug` output chunk `CONVERSATION_RESET_LINE` ("conductor: the earlier conversation isn't on this machine; starting a fresh one"). Without this a requeue to another machine resumed the same id forever (each Retry exited 1).
- **`start_failed: …`** (a `start_session` refusal: the daemon tried to spawn Claude and couldn't, e.g. `spawn ENAMETOOLONG`). The same machine will usually fail the same way, so these are **counted**: `retry_counters.start_failed` (`START_FAILED_COUNTER`) goes up on each one, and a matching `session.started` clears it. Below `MAX_START_FAILURES` = 3 in a row → requeue, as above. The third → no requeue: the counter is cleared and the session goes to a human, kind `retries_exhausted`, question "Could not start "<state>": the machine refused it 3 times in a row (<reason>). Retry, skip, or abort?". In an agent state that is the fallback human state; in a gate step's review phase it is the step's `on_unmet.else` ("Could not start the reviewer to <goal>…"), nothing killed. Other reasons (`ack_timeout`, `max_sessions`, `memory_pressure`, `no_conversation`) are never counted: they clear on their own or are handled above. Before this (NCNG-2630 on PC115, 2026-11-04) a reviewer's `spawn ENAMETOOLONG` was requeued about 1,400 times in two hours.
- **The system prompt on Windows.** The daemon passes `--append-system-prompt` (conductor's instructions plus the repo's CLAUDE.md, up to `MAX_CLAUDE_MD_BYTES` = 64 KiB) on the command line only up to `MAX_ARGV_SYSTEM_PROMPT_CHARS` = 8 KiB. A longer one is written to `system-prompt.md` in the session's private directory (beside `mcp.json`, owner-only, removed with it) and passed as `--append-system-prompt-file`, because Windows caps a command line at 32,767 characters. Both daemons (`spillSystemPrompt` / `spill_system_prompt`).
- `send_input` with `no_live_process` → `agent_process_live = false`, then re-answer with `start_session {resume_claude_session_id, prompt = pending_answer.answer}` ([Pending answer](#pending-answer)). Other `send_input` reasons → outcome `fail`.
- `run_cmd` → outcome `fail` (e.g. `memory_pressure`, `unknown_session`). In an entry step's checks phase (ADR-0010) → `on_unmet.else` instead (the machine could not run the check: not the agent's fault).
- `run_action` (ADR-0010) → `on_unmet.else` with the reason; outside an entry step's actions phase `unexpected_event`.
- `kill` → ignored (`kill_refused`; logged as the event row).
- `send_message` (any reason: `no_live_process`, `agent_parked`, …) → ignored (`message_refused`). A live message is best effort and never re-routes the workflow, unlike `send_input`'s `no_live_process` re-answer. After the commit the gateway appends a `debug` output chunk `conductor: message not delivered to the agent (<reason>)` so the board shows it ([ADR-0007](../adr/0007-live-messages-to-agents.md)).

## Fresh conversation

The manual escape hatch for an agent whose Claude conversation is broken in any way the [`no_conversation` refusal](#refusals) doesn't catch (a corrupt transcript, Claude crashing on every `--resume`, or the human just wants a clean slate). UI: "Start fresh conversation…" on the pending request ([06](06-human-input.md#session-detail-panel)).

- **Route.** `POST /api/sessions/:id/fresh-conversation` `FreshConversationRequest {text}` (trimmed, 1–20 000 chars; required) → `human.fresh_conversation {text, actor: 'ui', input_request_id: <the open input_request's id, or null>}`. 202; 409 `conflict` when ignored (message: the session is not waiting on a human with an agent to return to); 404 unknown session; 400 bad body.
- **Accepted** only while parked: `status = needs_input` in a `human` state whose `return_to` names an `agent` state, outside a gate step, and not a [revoked](#machines-protocol-v2) park. Anything else → `wrong_status` (`session_terminal` for a finished session).
- **apply.** (1) A live parked process (`agent_process_live`, e.g. after `ask_user`) is ended: `kill {target_command_id: agent_command_id}`, then `agent_command_id = null`, `agent_process_live = false`. (2) `claude_session_id = null`; when it was set, a `conversation_reset {claude_session_id: <old>, reason: 'user_requested'}` effect. (3) `return_to` is entered as `input.provided` would (never `send_input`), with `pending_answer = {input_request_id, answer: text}` and `skipEntry` (the session was already in that state). `state_entered` records `{transition: 'fresh_conversation' (FRESH_CONVERSATION_MOVE, not a workflow transition), reason: text, actor: 'human'}`. With no id to resume, the `start_session` has `resume_claude_session_id: null` and the state's full rendered prompt with the text as "Answer from a human" ([Pending answer](#pending-answer)); the daemon pre-assigns a new id. (4) No machine (`machine_id` null), or leaving a [lost-machine](#machines-protocol-v2) park (the pin is kept, as for "Continue"): `enter` requeues, keeping the pending answer, and the `session.assigned` re-emit starts fresh with it. `state_visits[return_to]` increments (as every `enter` does); retry counters, context, the branch and the worktree are untouched.
- **Wrapper**: answers the open input_request and bumps the fencing token ([EngineService wrapper](#engineservice-wrapper)).

## Agent process correlation

`session_event started` and `exit` carry the `command_id` of the `start_session` that spawned the process; `started` is emitted **only for `start_session`, never for `run_cmd`** (both reference workflows start with an agent state). The snapshot keeps `agent_command_id` (set by the wrapper on each `start_session`) and `agent_process_live`. apply ignores `session.started` / `agent.exited` whose `command_id` differs from `agent_command_id`, so a late exit of a previous visit's process (e.g. after `implement → build → fail → implement`) can't fail the current visit. A matching `session.started` sets `agent_process_live = true`; a matching `agent.exited` sets it false (outcome `fail` only while `running` without a prior `complete_state`). The `fail` question names how it ended and, when the daemon sent `exit.stderr_tail` (its last `STDERR_TAIL_LINES` = 20 stderr lines, ≤ `STDERR_TAIL_CHARS` = 4000), the last non-empty stderr line, clipped to `EXIT_STDERR_LINE_CHARS` = 300: "the agent exited (exit code 1: No conversation found with session ID …) without calling complete_state" (a reviewer's exit the same way). Like `command.exited.output_tail`, the raw `stderr_tail` is never persisted: the `agent.exited` event row stores `stderr_tail_bytes` (its UTF-8 length) instead, and only the clipped line reaches Postgres, in `input_request.question`. While `agent_process_live` is false, `input.provided` resumes with `start_session(resume)` instead of `send_input`. An ignored `session.started` (mismatched `command_id`, including `agent_command_id = null`) means a process is running that the session doesn't own: the gateway sends the orphan kill below.

## Orphaned processes

A Claude process whose `start_session` the orchestrator has given up on (ack timeout, or superseded) must be killed; nothing else will, and a re-claim can put a second process on the same worktree. This is the one place the rule lives:

1. **State**: `command.refused` for `start_session` (any reason, including `ack_timeout`) sets `agent_command_id = null`, `agent_process_live = false`, and the wrapper bumps `fencing_token` ([Refusals](#refusals)). The session can't move `queued → running` from the orphan's `started`, and its other events are rejected as stale.
2. **Late accepted ack**: T11, on `command_ack accepted=true` with row count 0, reads the row by `command_id`; if it is a `start_session` with `status = 'failed'` and `session.agent_command_id` is not that `command_id` (if it still is, the refusal was ignored because `started` came first, so the process is owned), it sends a direct `kill {command_id: null, target_command_id: <that command_id>, reason: 'ack_timeout'}` to the acking machine (envelope `session_id` = the row's, `fencing_token` = the session's current token). Other row-count-0 acks stay ignored.
3. **Ignored `started`**: when apply ignores a `session.started` for a mismatched `command_id` (`ApplyEventResult` `{status: 'ignored', reason: 'command_id_mismatch'}`, a member of `APPLY_IGNORE_REASONS`), T11 sends a direct `kill {command_id: null, target_command_id: <started.command_id>, reason: 'superseded_start'}` to the sending machine, after the commit. (An ignored `agent.exited` needs no kill: the process is gone.)
4. **Stale fencing**: a `session_event` rejected for its fencing token gets the existing direct `kill {command_id: null, target_command_id: null, reason: 'stale_fencing_token'}` with the *event's* fencing token in the envelope. A `heartbeat` that lists a running session under a token lower than `session.fencing_token` gets the same kill (with the listed token); this is the backstop that needs no further event from the orphan.
5. **Daemon kill rule** (T05, `KillPayloadSchema` in `ws.ts`): with `target_command_id` set, kill only the process spawned by that `start_session` (none live → no-op); with it null, kill the session's process only if its fencing token ≤ the envelope `fencing_token`. So no orphan kill can hit the process of a newer claim of the same session on the same machine. A process is signalled (its whole process group) and logged once, however often its kill arrives.
6. **Terminal session** (BUG-1): a session never ends with its agent process running. apply's move into a terminal state kills the live agent process: entering a `terminal` state emits `kill {target_command_id: agent_command_id}` when `agent_process_live`; `failSession` (cancel, fail) emits its session kill (null target). A human move (`human.transition`, `input.provided` with a `goto`) off a parked agent into a state that runs no agent (command, event, connector, human) kills it the same way (targeted, lead decision 2026-10-27). A lost machine (M2-T06) keeps its own `machine_lost` kill decision, with no second kill. All of these then set `agent_command_id = null`, `agent_process_live = false`. The wrapper bumps the token ([EngineService wrapper](#engineservice-wrapper)), so if that kill is lost, rule 4 is the backstop: the daemon's next heartbeat lists the process under the old token and gets a `stale_fencing_token` kill; a `start_session` that had not yet reported `started` is killed the same way when its `started` arrives stale.
7. **Daemon side** (BUG-1): a `start_session` that supersedes an earlier one for the same session kills the earlier process; one that arrives while an earlier start is still preparing its worktree makes the earlier one refuse (`superseded`) before it spawns. The daemon persists each agent's `{pid, claudeSessionId, startedAt}` (`startedAt`: the process start time from `ps lstart`, read at spawn) in its local store. On startup it kills a process the previous daemon left running (Claude runs in its own process group, so it can outlive the daemon) only if it is provably ours (BUG-1b): the pid is alive, its start time equals `startedAt`, its argv is the configured Claude binary (argv[0], or argv[1] after a `node` interpreter, as for a `#!/usr/bin/env node` launcher) with `--session-id <id>` or `--resume <id>` as adjacent tokens, and the stored id is a UUID. It signals the process group only (never a bare pid) and repeats the check before the SIGKILL after the grace period. Anything else (a user's own `claude --resume`, a process that only mentions the id, a reused pid, an old entry without `startedAt`) is left alone and logged, and the entry is cleared. It then reports the `daemon_restart` exit as before.

Kills are direct replies, not outbox rows: if the socket drops before one is written, the orphan's next stale-token event or the next heartbeat after reconnect triggers rule 4.

**Accepted gap (U-023, M1).** A `superseded_start` kill (rule 3) lost to a socket drop is not re-triggered: the replayed `started` is deduped on `seq`, and the orphan holds the current fencing token, so rule 4 misses it. Accepted for M1 because it needs a socket drop inside a narrow window on a single machine, and the orphan dies when the session's worktree is cleaned up (its cwd is removed and the daemon kills every process it spawned under that worktree). Revisit with multi-machine (M2). BUG-1 narrows the gap: once the session is terminal its token is bumped, so rule 4 catches such an orphan at the next heartbeat.

## Pending answer

`session.pending_answer {input_request_id, answer} | null` ([02](02-data-model.md#session), `SessionSnapshot.pending_answer`) keeps a human answer until an agent is running on it, so no path loses it ([U-026](../tracking/UNKNOWNS.md)):

- **Set** by apply on `input.provided` (alongside the wrapper's `input_request.answer` write), on `human.transition` / `human.fresh_conversation` into the asking agent, or by [Reopen](#reopen) on the new session's INSERT (`input_request_id: null`: it answers no request, and is never sent through `send_input`).
- **Used**: every `start_session` apply emits while it is set uses `prompt = pending_answer.answer` with `resume_claude_session_id`: the `input.provided` resume when `agent_process_live` is false, the `send_input` `no_live_process` re-answer, the resume after `agent.exited` while parked, and the `session.assigned` re-emit after a refused or timed-out resume requeued the session. After a `no_conversation` refusal there is no conversation to resume (`claude_session_id` is null), so that re-emit renders the full state prompt with the answer in it instead ([Refusals](#refusals)).
- **Cleared** when the agent is running on it: a matching `session.started`, or, on the live `send_input` path (an accepted ack is not an engine event), the agent's next `agent.complete_state` / `agent.ask_user` / `agent.no_outcome`. Entering a state (apply's `enter`):
  - a **different** state clears it, unless that apply delivers the answer (`input.provided`);
  - an `input.provided` into an **agent** state keeps it: for the live `send_input` (kept until the agent's next outcome, as above), for the `start_session` that uses it (kept until that start's matching `session.started`, so an `ack_timeout` requeue can re-answer), or, when the session has no machine, through the requeue until the `session.assigned` re-emit;
  - re-entering the **same** state (a self-loop) keeps it for the re-answer;
  - entering any non-agent state (command, connector, event, human, terminal) clears it.

  Always cleared on terminal statuses and on `operator.cancel`.

## Prompt render

`apply()` renders every `start_session.prompt` with `renderPrompt` (`shared/src/engine/render.ts`; [05](05-workflow-engine.md#prompt-render)); it is the only renderer ([U-040](../tracking/UNKNOWNS.md), M1-T07 deleted the wrapper's `engine/prompt.ts`). The wrapper and the dispatcher pass the prompt through verbatim. A resume whose prompt is `pending_answer.answer` sends the human's text unrendered.

## Requirements review (ADR-0009) and entry steps (ADR-0010)

Semantics: [05 §Requirements gates](05-workflow-engine.md#requirements-gates-adr-0009) and [05 §Requirements to enter a column](05-workflow-engine.md#requirements-to-enter-a-column-adr-0010). One representation, the gate step. The contract points:
- **Snapshot.** `SessionSnapshot.step: GateStep | null` (`{kind: 'transition'|'entry', from, outcome, to, attachment, subject, claude_session_id, nudged, phase, index}`). While set, `workflow_state` is `reviewStateLabel(from, to)` = `"<from> → <to> (review)"` or `entryStateLabel(from, to)` = `"<from> → <to> (entry)"`, and `apply` routes every event through its step handler (anything else is ignored with the existing reasons: `unexpected_event`, `wrong_status`, `command_id_mismatch`, `stale_timer`). Stored in `session.context[STEP_CONTEXT_KEY = "__entry"]` by `writeSession`, lifted out by `toSnapshot` (`orchestrator/src/engine/rows.ts` `joinStep` / `splitStep`, which also reads the pre-ADR-0010 `__review`); never in `GET /api/sessions/:id`'s `context`, never carried by a reopen.
- **Entry checks / actions.** A check is a `run_cmd {state: <label>, cwd: null, timeout_ms}` whose `command.exited` is the check's outcome; an action is a `run_action {state: <label>, target_state, action, idempotency_key: "<session>:<to>:<visit>", args}` whose `action.completed` is its outcome (`result` merged into `context.<to>`). Unmet counter `entryCounterKey(to)` = `"entry:<to>"`; feedback heading "Requirements to enter <title> were not met:" (`feedbackHeading`). Deadlines: none during checks (the daemon times them out), `REVIEW_TIMEOUT` (10m) for the review, `ENTRY_ACTION_TIMEOUT` (10m) for an action. Checks carry `run_cmd.checkout = {sha: step.head_sha (null for the first), setup: entry.setup ?? null, last}` (not the implicit pin check) and run in a fresh checkout of that commit; `command.exited.setup_failed` → unmet, item "Setup". `command.exited.not_run` (the check did not run, and why) → unmet, item the check, reason "`<cmd>` did not run: <why>" (never "killed by a signal"); `command.exited.no_commits` (the branch adds no commits to origin's default branch) → straight to `on_unmet.else` (a human: there is nothing to check or to open a PR for), no retry counted. Checks also carry `run_cmd.require_clean: true`; `command.exited.dirty` (the status lines) means the tree had uncommitted changes and the check did not run: unmet, item "Committed work". `command.exited.head_sha` (optional) is the commit a check ran on: recorded from the first check as `step.head_sha`, compared on later ones, passed as `run_action.expected_sha`, and named in the review prompt. open_pr's URL goes only to `context.__pr` (`PR_CONTEXT_KEY`), validated against `GITHUB_PR_URL_RE` by the daemon, the engine and `BoardCardSchema` (invalid → null).
- **Reviewer start.** `start_session {state: <label>, tools: REVIEW_TOOLS = ['review'], resume_claude_session_id: null, model: gate.model?, max_budget_usd: remaining, review: true}`, prompt `renderReviewPrompt` (first line `REVIEW_PROMPT_HEADING`). The one nudge resumes `review.claude_session_id` (the reviewer's) with `reviewNudge(why, items)`. The wrapper treats it like any start (new `agent_command_id`, `agent_process_live = false`).
- **Claude sessions.** `agent.claude_session_id` during a review sets `review.claude_session_id`, never `claude_session_id`; the daemon does not store a `review: true` start's id as the session's (`PersistedSession.claudeSessionId`), so transcripts (ADR-0008) and reopen stay on the worker's conversation. `spend.reported` is per Claude session id as always, so reviewer spend adds to `spend_usd`.
- **Verdict.** `parseVerdict(result, items)`; kept as `context[<label>] = {verdict: [{item, met, reason}]}`. Unmet loop counter `reviewCounterKey(from, outcome)` = `"requirements:<from>:<outcome>"`. The worker's next prompt gets `renderReviewFeedback` via `RenderPromptInput.feedback`.
- **Leaving.** `workflow_state` goes back to `from`, `agent_command_id = null`, `agent_process_live = false` (the reviewer's late `exit` is then a `command_id_mismatch`), then the next state is entered with `state_entered.from = <label>`. A `kill` is emitted on the timeout, no-verdict and budget paths.
- **Timeout.** `REVIEW_TIMEOUT` = `10m`, armed as `state_deadline` with `set_deadline(<label>, …)`; the sweep's `timer.fired {state: <label>}` matches it.

## Transitions (ADR-0011)

Semantics: [ADR-0011](../adr/0011-transition-rules.md) (accepted, with Ben's answers to U-058, U-059, U-061..U-063) and [05 §Transition object](05-workflow-engine.md#transition-object-adr-0011). Frozen by M1b-T01; groups B–D report a needed change to the lead. The contract points:
- **Definition.** `on` keys are transition names. Transition object: `goto` (a state or `RETURN_TO` = `"$return_to"`), `title?`, `when?`, `actor?`, `kinds?`, `question?`, `requires?` `{checks?, setup?, review?, actions?, conditions?, condition_timeout?, condition_poll?}`, `on_unmet?`, plus the M1 / ADR-0009 fields. `ConditionSchema` is a union on `type`: `pr_checks_green {no_checks_after?: duration}` (ADR-0025, U-072: the engine's rule, never sent to the daemon), `pr_approvals {min ≥ 1}`, `pr_merged`, `pr_screenshots {ui_paths: glob[1..50], min_pairs?: 1..20}` (M2-T35a, below), `azure_pipeline_succeeded {pipeline}`, `jira_fields_set {fields[1..20]}`, each with `enabled?` (default true) and `label?`. `AVAILABLE_CONDITION_TYPES` (the first four, plus ADR-0037's `cmd`, `pr_mergeable`, `age_below` since T5, [below](#workflow-primitives-adr-0037)) and `AVAILABLE_TRANSITION_ACTIONS` (`open_pr`) are what M1b runs; the rest parse, the validator refuses the actions (rule 14), and the daemon answers the conditions `unsupported`.
- **`pr_screenshots`** (M2-T35a, Ben 2026-10-29: a PR with a UI change carries before/after screenshots). The daemon's `gh pr view` adds `files,changedFiles,body` only when this condition is evaluated, and its `--jq` keeps the changed paths and the pair count of the body's marker `<!-- conductor:screenshots pairs=N -->` (`screenshotsMarker`, written by `open_pr` with the Before / After table, M2-T35b), never the body. **met** when no changed path matches `ui_paths` (`globToRegExp`: `**`, `*`, `?`, `{a,b}`) and gh listed every file (`changedFiles` ≤ the 100 gh lists), or when the marker counts ≥ `min_pairs` (default 1); otherwise **failed**, the detail naming the UI files and telling the agent to save `before-<view>.png` / `after-<view>.png` in `$CONDUCTOR_SCREENSHOT_DIR` (M2-T35b) and finish again, so the move goes back through `on_unmet` like a red check. It is a PR condition (head pinning, failed at once without a PR). Shared helpers: `shared/src/workflow/screenshots.ts` (`DEFAULT_UI_PATHS`, `SCREENSHOT_NAME_RE`, `screenshotPairs`). A daemon before M2-T35a refuses the args (TD-195).
- **Actor and kind.** `transitionActor` infers the actor ([05](05-workflow-engine.md#transition-object-adr-0011)): explicit, else `system` for the system names and `wait_for` events, else `agent` on agent states, `human` on human and event states, `system` on command and connector states; T02's rule 10 rejects an explicit `actor: 'agent'` on a non-agent state. `transitionMatchesKind(t, kind)`: `kinds` omitted → both, ticket kind null → both (U-062). `agentTransitionOptions(def, state, kind)` is the one list of what an agent may name: the prompt's "How to finish" (T03) and `start_session.transitions` are both built from it. `humanTransitionOptions(def, state, kind, return_to)` is the one list of buttons.
- **Agent outcome.** The tool input is `CompleteStateInputSchema {transition?, reason?, result}` (caps at the tool call; the WS event is uncapped). `session_event complete_state {result, transition?, reason?}` → `agent.complete_state {result, transition?, reason?}` (the gateway passes them only when present; absent ≡ null ≡ `done`). Context write: a completing transition stores `result` as `context[<state>]` after its keys and guard pass; a `question: true` transition stores a non-empty `result` there without either check (an empty one writes nothing), so `GET /api/sessions/:id` shows e.g. the plan of `plan_needs_approval`. An agent naming a transition it may not take is **not** an ignore: apply routes it to needs_input (`agent_question`, question `unknownTransitionQuestion(name)`). `unknown_transition` / `transition_not_allowed` are ignore reasons for `human.transition` only.
- **Human move.** `POST /api/sessions/:id/transition` `TransitionSessionRequest {name, text?}` → `human.transition {name, text: text ?? null, actor: 'ui', input_request_id: <the open input_request's id, or null>}` (apply answers a parked live agent with `send_input {input_request_id}`). Accepted from a human state, or an event state for an `actor: human` transition; `RETURN_TO` resolves to `return_to`. The wrapper answers the open input_request ([EngineService wrapper](#engineservice-wrapper)). `/input` keeps working (T03 maps it onto the same path).
- **Counting.** `isCountedTransition(t)`: only an object with `attach`, `retries` or `else` is a counted `<from>-><goto>` failure loop; any other object transition is a plain forward move. Requirement retries count under `moveCounterKey(from, name)` only. T02 (rule 4) and T03 (apply) must use the helper ([05 §Counting](05-workflow-engine.md#counting-adr-0011)).
- **Move step.** `requires` on a taken transition runs as `GateStep {kind: 'move', transition, actor, reason, …}`, phases `checks → review → actions → conditions`, label `moveStateLabel(from, to, name)` = `"<from> → <to> (move: <name>)"`, counter `moveCounterKey(from, name)` = `"move:<from>:<name>"`, feedback heading `feedbackHeading({kind: 'move', title})` = "Requirements for <title> were not met:". Old versions keep `entry` / `transition` steps. New step fields all default (`transition`, `actor`, `reason` null; `conditions` []; `conditions_deadline`, `conditions_poll_ms`, `conditions_started_at`, `conditions_note` null), so M1 rows parse.
- **Conditions phase** (U-058, U-059, U-063). Status `waiting_external`, card in the source column, worker ended, no wall time, no machine slot held (04 §1). Exception: when the only unmet conditions are `pr_approvals` (`awaitingApprovalOnly`, judged by each condition's last `answer` while an evaluation is `running`), the card shows in the first event column (Waiting external), still badged `checking`. This is display only: the step is unchanged. The engine emits `run_action {action: 'evaluate_conditions', args: EvaluateConditionsArgs {conditions (enabled ones, in order), pr_url: context.__pr.pr_url ?? null, branch, head_sha?}}` on the session's machine; no new outbox kind; `idempotency_key` = `conditionsIdempotencyKey(session, label, now)` (informational), `args.branch` informational (the daemon uses its own record). `head_sha` is optional, 40 hex: the commit conductor checked and pushed (ADR-0010 `expected_sha`); the engine passes `step.head_sha` when it has one, and the daemon then fails every PR condition whose PR head (`headRefOid`) differs ("someone pushed to the branch"). The daemon acks, then reports `action_result {result: EvaluateConditionsResult {results: [{type, status: met|pending|failed|unsupported, value, detail}]}}`, one per condition in order, matched by position → `action.completed`. `pr_checks_green` with no checks at all answers `pending` with `value` `NO_PR_CHECKS_VALUE` (`"0/0 passed"`, `shared/src/protocol/ws.ts`), which the engine's `no_checks_after` grace keys on (timed from `step.conditions_started_at`, ADR-0025); a failed one's detail lists each failing check with its https link. `step.conditions` holds one `ConditionStatus {type, label, status, value, detail, checked_at}` per **declared** condition (disabled ones `disabled`). All met → enter `to`; any `failed` → `on_unmet.goto` with the evidence, counted; `condition_timeout` (`step.conditions_deadline`) → `on_unmet.else`; else re-poll after `conditions_poll_ms` (from `condition_poll`, default `DEFAULT_CONDITION_POLL` 2m, doubling to `MAX_CONDITION_POLL` 15m). A refused or timed-out evaluation keeps it pending with `conditions_note = CONDITIONS_NO_MACHINE_NOTE`. No human override while conditions are pending (Ben: stay until met); `operator.cancel` and an event state's `ui.approve` still interrupt.
- **Card.** `kind`, `pending`, `human_transitions` (and `checking`) default to null / null / [] / null in `BoardCardSchema`, so pre-M1b `card.upserted` rows still parse. `BoardCard.kind` (null for older tickets); `pending` `{transition, to, title, items: [{label, status, detail}], note}` from `pendingOfStep(def, step)` for any gate step (supersedes `checking`, which is kept for one release; `checking.phase` gains `conditions`); `human_transitions` `[{name, title, goto, needs_text, presets?: [{slug, label, text}]}]` while `needs_input` in a human state or `waiting_external` in an event state, outside a step. `needs_text` (`transitionNeedsText`): `RETURN_TO` or an event-state target.
- **Checking (UX-5).** In a gate step `BoardCard.checking` = `checkingOfStep(def, step)`: today's `{to, title, phase}` plus optional `label` ("Checks before <transition title>"; "Review before …" for an ADR-0009 review), `transition`, `items: [{label, kind: check|review|action|condition, status, detail}]` in run order (the same items as `pending`, `met` read as `passed`) and `current` (the running item's index, else null). The fields are optional on the wire, so older payloads parse; the board shows "Conductor is checking · <item> (n/m)" from them instead of a running agent. No per-item durations yet (TD-152): M2c persists check runs with their times (ADR-0019). There is no `setup` phase: the fresh checkout's setup runs inside the first check's `run_cmd` and reports nothing separately.
- **Moves.** `SessionDetail.moves?` = the last 50 `state.entered` rows as `MoveDto {at, from, to, transition, reason, actor, cause?}` (`toMoveDto`; optional on the wire so older servers parse). `cause` (ADR-0037 P7) is null on rows written before it. An engine move (`isEngineMove`: a cause in `ENGINE_CAUSES`, or actor `engine` on an older row) is not a named transition (`isNamedMove`); the timeline words it by `causeTitle`, an older row by `engineMoveTitle`.
- **Ticket body (UX-2).** `SessionDetail.ticket_body?` = `ticket.body` (the session panel's Brief parses its markdown sections); optional on the wire so older servers parse. The web falls back to the transcript's first `user` chunk when it is absent.
- **Input requests (UX-7).** `SessionDetail.input_requests?` = the session's `input_request` rows, answered or not, the last 50 (`SESSION_INPUT_REQUESTS_LIMIT`), oldest first (newest last): `{id, kind, question, created_at, answer, answered_at, truncated}`. Question and answer are clipped to 4096 characters (`INPUT_REQUEST_TEXT_LIMIT`), and `truncated` says one was. The Details tab shows each answer next to the move it caused (an answered `input.provided` writes a move with no transition or reason). Optional on the wire so older servers parse; absent ≡ [].
- **Ticket kind.** `TicketKindSchema` `work | personal`. `ticket.kind` is M1b-T04's migration; `TicketRow.kind` lands with it (the schema test holds row types equal to the DDL), and until then readers use `kind ?? null` (`toSnapshot`, `CardTicketLike.kind?`). `CreateTicketRequest.kind` is optional (WF-T03): when absent, `createTicket` takes the kind of the account's most recent ticket on the same (canonical) repo (`lastTicketKind`, skipping null kinds); with no earlier ticket there it returns 400 `bad_request`, details path `kind`. An explicit kind always wins, and a ticket is never stored without one.
- **Legacy fold.** `foldLegacyRequirements(def)`: `entry` → every non-fallback transition into the state; ADR-0009 `requirements` → `requires.review` + `on_unmet`; gate items first, gate model and `on_unmet` win, existing `requires` fields win. The engine never folds.

## Workflow primitives (ADR-0037)

- **Notifier seam (P6, T4).** With the definition's `notify` block, `apply()` records the decision as `notify_decision` on the `state_entered` effect (stored as the `state.entered` payload's `notify`) and on `create_input_request` (stored as `input_request.notify`, migration `1763600000000_notify-policy`). The wrapper writes one push per positive decision: `push_needs_input` when the landing opens a request, else `push_transition` (and its `transition.notified`); a silent decision writes none. With `coalesce` the idempotency key is `notify:<ticket>:<state>:<floor(now / coalesce)>` (`notifyBucketKey`). - **`once` memory (P6, T4).** The snapshot gains `notified_transitions?: string[]` (`session.notified_transitions text[]`), the `once` transitions that already pushed; `apply()` appends to it, and a reopen copies it to the new session. See ADR-0037 P6.
- **Short-circuit (P1).** `EvaluateConditionsArgs` gains `short_circuit?: boolean`. When it is set, the daemon stops at the first non-`met` result and reports the rest as `skipped`, a new `ConditionResult.status` and `ConditionStatus` value (and `BoardCheckingItem.status`).

- **Mergeability (P3).** `ConditionResult` gains `mergeable?: 'MERGEABLE' | 'CONFLICTING' | 'UNKNOWN'`, set on a `pr_checks_green` result whose condition has `no_checks.policy: require_mergeable`. Fixtures: `M1B_WS_FIXTURES.run_action_evaluate_conditions_adr0037` / `action_result_evaluate_conditions_adr0037`.
- **Watch and hold triggers (P1/P4). The orchestrator feeds `watch.check` and `concurrency.checked {holders}` events to `apply()`. They are sent on the poll timer, and to every session on the same repo when a PR merges (`merge_pr` ok, or a human move to a terminal state with `context.__pr`) or conductor pushes a branch.

## Review and merge (ADR-0020)

Semantics: [ADR-0020](../adr/0020-review-and-merge-flow.md). Frozen by M2r-T01; later M2r tasks report a needed change to the lead. - **QA result** (`engine/qa.types.ts`). `QaResultSchema` = `{verdict: pass|pass_with_debt|fail, requirements?: [{req ≤ 40, met, reason ≤ 1 000}] ≤ 50, findings: [{severity: blocker|major|minor|nit, text, file?, line?}] ≤ 50, required_fixes: text[] ≤ 20, debt: [{text, site?, payoff?}] ≤ 20, unknowns: [{question, why}] ≤ 10, tests_run: [{cmd, result: pass|fail, note?}] ≤ 20, summary ≤ 2 000}`; every `text` ≤ 1 000 (`QA_LIMITS`). - **Actions** (`protocol/actions.ts`; `GitShaSchema` = 40 hex, `PrUrlSchema` = `GITHUB_PR_URL_RE`). `OpenPrArgs {title, body}`; `OpenPrResult {pr_url, head_sha?}` (the pushed commit; optional for older daemons). `InspectPrArgs {pr_url, approval_paths: Record<id, glob[1..20]> (≤ 5)}` → `InspectPrResult {head_sha, files ≤ 300 (PR_FILES_MAX), files_truncated, mergeable: MERGEABLE|CONFLICTING|UNKNOWN, state: OPEN|CLOSED|MERGED, matched: Record<id, path[] ≤ 300>}`. `MergePrArgs {pr_url, expected_sha, method: 'merge', approved_paths: path[]}` (ADR-0020 §4: a flat list of approved files) → `MergePrResult` = `{ok: true, merged: true, already, merge_commit_sha, head_sha, note?}` \| `{ok: false, unmet: head_moved|conflict, observed_sha?, detail}` \| `{ok: false, error: closed|blocked|approval_missing|error, detail}` (the failure shapes are strict; `detail` / `note` ≤ 2 000). `ClosePrArgs {pr_url | null, reason ≤ 20 000}` → `ClosePrResult {closed, merged, already}`. **Reporting:** `inspect_pr` / `close_pr` / `open_pr` put success in `action_result.result` and a failure in `error` (a failed action → `on_unmet.else`); `merge_pr` reports every gh outcome as a `MergePrResult` in `result`, `error` only for unparseable args or a daemon fault.
- **WS** (`protocol/ws.ts`). `start_session.checkout? {sha, pr_url, setup: string | null}`: a QA start (`review: true`, `tools: ['qa']`) in a fresh checkout of `sha` from the trusted remote, with `qa-base` at the merge base; the daemon re-checks the PR head and the repo. A failed checkout refuses the start with `command_ack.reason` `checkout_failed: <sentence>` (`COMMAND_REFUSAL_REASONS`). `run_action.action` accepts `inspect_pr`, `merge_pr`, `close_pr`. **Open seam:** `commandPayloadForEffect` still throws for them, and the daemon's `runAction` sends every action other than `evaluate_conditions` to `openPr`: M2r-T05 must dispatch (or refuse) them explicitly before T03 / T04 widen the mapping.
- **Engine** (`engine/types.ts`). `human.transition.approvals?: id[] ≤ 5` (absent ≡ []). Ignore reasons `approval_required` (an active approval not ticked) and `pr_open` (into Done with an open PR, merge-aware definitions). `GateStep.approvals: {who, ids, files: Record<id, path[]>} | null` (default null: older rows parse). ## Wall time

`session.wall_seconds` is maintained by apply (T04), which gets `now`: on every state transition it adds `now − state_entered_at` for the state being left, then sets `state_entered_at = now`. Time in `human` and `event` states is not added (parked time doesn't count toward `budget.minutes`, [09](09-security-and-budgets.md#budgets)). A requirements review's time is added when the review step is left, as part of its source state's ([ADR-0009](../adr/0009-transition-requirements-review.md)). Nothing else writes it. M1 has no enforcement trigger on it (like `budget.exceeded`, TD-015).

## Guards

A state's `guard` names an evaluator in `GUARD_REGISTRY` (`shared/src/workflow/guards.ts`): `(input: {def, snapshot, result}) => boolean`, pure. apply (T04) calls `evaluateGuard(name, input)` on `agent.complete_state` before leaving the state; false → the state's `fail` outcome, or `needs_input` if the state has no `fail`. **The M1 registry is empty and an unregistered guard fails closed** (`evaluateGuard` returns false → the state's `fail` outcome, or `needs_input` if it has none; TD-017). The validator (T03) accepts any guard name, so both reference workflows validate. `pr_flow`'s `open_pr` therefore always routes to needs_input in M1 (pr_flow isn't an M1 workflow); registering it needs commit facts in the `complete_state` event, and at that point an unregistered guard becomes a validator error.

## Tools

`TOOL_ALIASES` (`shared/src/workflow/tools.ts`) maps each workflow `tools` name to an ADR-0005 `ToolPolicy` fragment: `read` (base only), `edit` (`Edit(./**)`, `Write(./**)`: path-scoped, never bare), `bash` (`npm run:*`, `npm test:*`, exact `npm install` / `npm ci`; M2-T30: `pnpm run:*`, `pnpm test:*`, exact `pnpm install` / `pnpm i` (each also with `--frozen-lockfile`), `pnpm exec vitest:*`, `pnpm exec prettier:*`, `chmod +x:*`; M2-T30b: exact `pnpm typecheck` / `lint` / `build` / `format`, `pnpm vitest:*`, `pnpm exec eslint:*`, exact `pnpm exec tsc -b`; no interpreters or general runners, no bare `pnpm exec` / `pnpm dlx`), `git` (exact inspection commands, because diff/log/show accept `--output=<file>`, plus `add:*`, `commit:*`, `restore:*`; Claude Code also auto-allows commands it classifies as read-only), `pr_skill` (`Skill`, `gh pr view:*`; `gh pr create` is denied because it can push, so the PR is opened by a trusted state, TD-020), `review` (the requirements reviewer, [ADR-0009](../adr/0009-transition-requirements-review.md): `Bash` visible, only the exact read-only commands in `REVIEW_GIT_COMMANDS` pre-approved (`git status`, `git diff`, `git diff --stat HEAD~1`, `git log -p -n 5`, `git show --stat`…); no prefix rules, no edit tools, no staging or committing). `resolveToolPolicy(tools)` merges `BASE_TOOL_POLICY` (worktree-scoped `Read(./**)`/`Glob(./**)`/`Grep(./**)`, deny `Bash(git push:*)`) with each fragment, de-duplicates, and drops any allow rule that is also denied; it throws `UnknownToolAliasError` on a name not in `TOOL_ALIAS_NAMES` (T03 validates against the same list). `git push` is always denied. Since [ADR-0006](../adr/0006-agents-inherit-claude-code-settings.md) the `builtin` list still limits the visible tools, but `allow` rules only **pre-approve**: the user's own Claude Code settings (mode and rules) decide everything else, and the edit-guard hook keeps file edits in the worktree. **These rules are not a sandbox**: `npm run` / `pnpm run` execute repo scripts the agent can edit, and `pnpm exec vitest` / `prettier` load config files it can edit (TD-019), so the security boundary is the OS-level sandbox (U-004, slice 3). Every alias that grants `Bash` also grants `BACKGROUND_TOOLS` (`TaskStop`, plus the older CLIs' `BashOutput` / `KillShell`, which a newer CLI ignores) in `builtin` and `allow`, so an agent can run long work with `run_in_background` and stop it again ([ADR-0035](../adr/0035-background-work-and-live-messages.md)). The daemon (T05) calls it on `start_session.tools`; the driver adds the conductor MCP tools.

**Cookies.** With an `https` public URL: `__Host-conductor_session=<base64url 32 bytes>; HttpOnly; Secure; SameSite=Lax; Path=/`. In `password` mode on a loopback `http` URL (tests and e2e only): `conductor_session`, without `Secure`. Only the SHA-256 of the value is stored. Sessions last 30 days absolute and 7 days idle.

**SSE and 401.** `EventSource` can't see a response status, so a 401 on a stream looks like any stream error. When the board or output stream errors, the web re-probes `GET /api/me`; a 401 there sends the user to `/signin?next=<current path>`.

**CSRF** (no token): `SameSite=Lax`, the strict Origin check above, JSON-only unsafe requests, and no CORS headers at all. Every `GET` is side-effect free (asserted by the M2-T21 route matrix). **`next` redirects** go through `safeNextPath`: a same-origin path with a single leading `/`, no backslash, no scheme, no control or whitespace characters, and re-checked after normalisation (`/..//x` → `/`); anything else → `/`.

**Board card fields.** `routing?: {missing_repo?, missing_capabilities: string[]}` appears on Queued cards only, when no **online** machine of the account can take the ticket (the repo first, then capability keys such as `cli:az:authed`). `alerts?: {kind: 'git_tamper', files, at}[]` holds the open alerts of the card's session. Both are absent, never null, when there is nothing, so pre-M2 cards and `toBoardCard` output are unchanged (M2-T16 fills them).

**Repo grammar.** `canonicalRepo(repo)` returns `host/org/repo` with the host lower-cased and the path case kept. Routing compares github.com org/repo **case-insensitively**, as GitHub does: M2-T16 matches on `lower()`. It accepts:
- `host/org/repo`;
- `https://host/org/repo` (no userinfo, port, query or hash);
- `ssh://user@host/org/repo`;
- scp-style `user@host:org/repo`;

each with an optional `.git` (any case: `.git`, `.GIT`, `.Git`) and trailing `/`. One `.git` is stripped, never two: a name still ending in `.git` after that (`app.git.git`) is null, because GitHub repo names can't end in `.git`. So `canonicalRepo` is idempotent (`canonicalRepo(canonicalRepo(x)) === canonicalRepo(x)`). Anything else is null. The grammar is duplicated in the daemon's `cloneSource`, `canonicalRepo` and `isCanonicalRemote` (TD-107).

**Versioning and auth.**
- The daemon sends `register.protocol_version = PROTOCOL_VERSION`; absent means 1, an M1 daemon. `daemon_version` (package version, plus `+<CONDUCTOR_BUILD_SHA>` when set) was already required and stays so.
- `password` mode: the WS upgrade must carry `Authorization: Bearer <credential>` (`DAEMON_AUTH_HEADER`). The gateway resolves machine and account from it before accepting the socket; an unknown or revoked credential is answered **HTTP 401 at the upgrade** (no socket), which the daemon treats like `CLOSE_UNAUTHORIZED`. **HTTP 403 at the upgrade is also fatal**, treated like 401 / `CLOSE_UNAUTHORIZED`: stop reconnecting, log why, exit non-zero (M2-T04 QA, 2026-10-27). The machine id is the credential's machine; `register.machine_id` must match it. A register with `protocol_version` < 2 is closed `CLOSE_PROTOCOL`.
- `local` mode: no header, `register.machine_id` from `CONDUCTOR_MACHINE_ID`, v1 accepted, `enrollment_token` ignored (removed from the schema in M2-T21).
- Close codes (with `CLOSE_REASONS` text, ≤ 123 bytes): 4000 replaced by a newer connection (M1-T11, reconnect is fine); **4001** revoked while connected and **4003** unauthorized: the daemon stops reconnecting, logs why and exits non-zero; **4005** protocol too old: the daemon logs "update the daemon: re-run the install command". Since [ADR-0021](../adr/0021-daemon-auto-update.md) a daemon that knows it fetches `/downloads/latest.json` and updates itself ([§Daemon auto-update](#daemon-auto-update)).

**Inventory.**
- Sent after every `registered` and whenever the scan changes (10-minute rescan, `SIGHUP`). Each `inventory` **replaces** the machine's previous repos and capabilities wholesale. Not durable (`seq` null): a new connection sends a fresh one. `hash` is the daemon's digest of the inventory, and `request_work.repos_digest` carries the latest `hash`.
- `git_identity_missing` (optional boolean, WF-T02): true when the daemon has no commit identity and agents commit as `conductor <conductor@localhost>`. The daemon resolves the identity once at startup, each field on its own: `CONDUCTOR_GIT_NAME` / `CONDUCTOR_GIT_EMAIL`, else `git config --global user.name` / `user.email` of the user it runs as, else `conductor` / `conductor@localhost`, which sets the flag and logs a warning. The gateway stores it in `machine.git_identity_missing` (absent = null, unknown), and the Machines page warns on true. It is **never** part of `hash`: it can't change within a process, and the hash stays identical between the TS and Rust daemons.
- A repo: `path` (the user's checkout, absolute POSIX, no `.`/`..`; unique per machine), `remote` (canonical `host/org/repo[/sub…]` per `CANONICAL_REMOTE_RE`, the M1-T14 grammar without scheme, user, port or `.git`, with a **lower-case host** and the org/repo case kept, as T01's `canonicalRepo` produces it; T16 compares github.com org/repo case-insensitively; `null` = no allowed remote: listed, never routed to), `default_branch`, `head_commit` (40 or 64 hex), `mode` (U-060: `reference` = worktrees of a daemon reference clone, the default; `checkout` = worktrees off the user's checkout, opt-in, with the tamper check).
- `repo_inventory` is deprecated since T16a and removed in T21. The gateway ignores it from a connection registered with `protocol_version` ≥ 2 (whose `inventory` owns `machine_repo`; the legacy list would delete those rows) and still stores it for v1 daemons.
- Daemon side (T10): the roots and per-repo modes live in `<root>/config.json` (0600; owner-only DACL on Windows, ADR-0024), set with `conductor-daemon config roots <dir…>` / `config repo <path> --mode reference|checkout` / `config show`. `CONDUCTOR_ROOTS` (`:`-separated) overrides the file's roots. Each scan re-reads the file, so a change applies on the next 10-minute rescan or at once on `SIGHUP`. The Rust daemon (MR-T11) also rescans when `<root>/state/rescan` appears (polled every 2 s, then removed), on every OS: `conductor-daemon rescan` (MR-T13) writes it. Windows has no `SIGHUP` (ADR-0024), so there the running daemon also rescans on Ctrl-Break (MR-T13b, `platform/signals.rs`); SIGINT/SIGTERM (Ctrl-C or the console closing on Windows) stop it with exit 0. `CONDUCTOR_TEST_REMOTE_ALIASES` (`<path>=<host/org/repo>,…`, tests only) applies only with `CONDUCTOR_ALLOW_LOCAL_REPOS`. `open_pr` refuses a `gh` older than `GH_MIN_VERSION` (2.40.0, a safe floor: U-076) before pushing anything.

**Capability keys.** `capabilityKey(c)` is the routing key; versions are never part of it:

| kind | key |
|---|---|
| `cli {name, version, authed}` | `cli:<name>:authed` when authed, else `cli:<name>` |
| `mcp {name}` | `mcp:<name>` |
| `skill {name, repo?}` / `agent {name, repo?}` | `skill:<name>` / `skill:<name>@<repo>` (same for `agent`) |
| `claude {version}` | `claude` |

A capability name follows `CapabilityNameSchema` (1–200 chars, no whitespace, `:`, `@` or NUL), the same rule as the names inside requirement keys, so every reported capability can be required. The daemon reports a plugin MCP server named `plugin:<plugin>:<server>` as `mcp:<server>`. A capability whose name is still invalid is not reported and is logged once per daemon process, not on every rescan (`inventory: capability <kind> "<name>" not reported: <reason>`); the rest of the inventory is sent as usual (M2-T10b). The other scan warnings are logged the same way: no repo roots configured, no git repos under the roots, and a repo whose `origin` can't be routed (`remote: null`). Each time an inventory with a new hash is sent, the daemon logs `inventory: sent <n> repos (<k> routable: <remote>, …) and <m> capabilities`, naming at most 10 remotes.

**Storage (T09).** `machine_capability` stores routing keys: a `key` text column, primary key `(machine_id, key)`, one row per element of `capabilityKeys(c)` for each reported capability (an authed cli gives both `cli:<name>` and `cli:<name>:authed`). The key includes `@<repo>` for a repo-scoped skill or agent, so `skill:review` and `skill:review@github.com/o/app` are separate rows. Other columns (kind, name, version, `detail`) are for display only; routing reads only `key`. `detail` is `{authed}` for a cli and `{repo}` for a repo-scoped skill or agent.

**Ingest (T16a, `gateway/inventory.ts`).** An `inventory` replaces the machine's `machine_repo` and `machine_capability` rows in one transaction, scoped to the connection's account (nothing for a revoked machine or another account's). An inventory repo's row has `repo = path` (unique per machine; two checkouts may share a remote), plus `remote`, `default_branch`, `mode` and `head_commit`. An `alert` is deduped on `(machine_id, seq)` with the `machine.last_seq` guard, stored as a `machine_alert` (`detail = {repo, files, at}`; `session_id` kept only for a session of this machine and account), and its session's card is re-sent (`card.upserted`): cards carry their session's open alerts as `alerts`.

**Matching (`satisfiesCapability`, the claim's SQL in T16, `missingCapabilities` for the badge).** A requirement is met when:
- its exact key is stored for the machine; or
- it is a bare `skill:<name>` / `agent:<name>` and the machine has `skill:<name>@<ticket.repo>` (the ticket's canonical repo). A repo-scoped skill or agent never meets a ticket for another repo.

The repo part of a key (`@<repo>`) is compared **case-insensitively** for github.com, like the claim's repo filter (`lower(machine_repo.remote) = lower(ticket.repo)`; lead decision 2026-10-27): GitHub org and repo names are case-insensitive, so `skill:x@github.com/Org/App` meets a ticket for `github.com/org/app`.

**Repo rules (ADR-0013 amendment 2026-10-30).** Besides the repo and the capabilities, a machine takes a ticket only when its own `machine.repo_allow` is null or has a pattern matching `ticket.repo`, and no **other** unrevoked machine of the account (online or not) has a `repo_exclusive` pattern matching it. A pattern is a canonical remote or `host/org[/sub…]/*`; it matches the same repo case-insensitively, or for `prefix/*` any repo under `prefix/` (`repoPatternMatches`; the claim's SQL is `REPO_PATTERN_MATCH_SQL`, `starts_with`, never `LIKE`). The badge reports `exclusive_to` (the holders' names, when none of them may take it now) and `excluded_by_rule` (an online machine's own allow-list leaves it out); when the rules allow no online machine, only those are reported. Only identical exclusive patterns conflict on save (TD-199).

A repo whose `remote` is null has its repo-scoped skills and agents **not reported** (`CapabilitySchema.repo` must be a canonical remote): they can't be matched to any ticket. `missingCapabilities(caps, reqs, ticketRepo)` is the list a Queued card's routing badge names.

**Alerts.** `alert {kind: 'git_tamper', repo, session_id?, files, at}`: in `checkout` mode the daemon hashes the checkout's `.git/config`, `.git/hooks/` and the `core.hooksPath` target before and after each session; a change raises one alert. `repo` is the inventory `path`; `files` (1–200) are relative to the checkout's `.git`. **Durable**: `seq` is required, so the daemon buffers and replays it like a `session_event`, and the gateway dedupes it on `(machine_id, seq)` with the same `machine.last_seq` guard ([Daemon seq dedupe](#daemon-seq-dedupe)).

**Working copy.** The claim (T16) chooses a `machine_repo` and writes `{repo_path, mode}` into `session.context.__working_copy` (`WORKING_COPY_CONTEXT_KEY`; no migration) in the claim transaction, before `applyEvent(session.assigned)`. apply keeps unknown context keys, and `commandPayloadForEffect` copies a valid `__working_copy` into **every** `start_session` of the session (first start, resumes, reviewer starts, the re-emit after a requeue), so no caller passes it. A re-claim by another machine rewrites it; a claim that matched no repo (a non-canonical ticket repo) removes it. When several of the machine's repos have the remote, the claim takes the first by `path`. The claim's filters are in [04 §2](04-scheduler.md#2--claim-query-ticket-side). The daemon:
- re-checks that `repo_path` with that `mode` is in its own current inventory, and refuses the start otherwise; it never uses a path it didn't scan;
- reuses its existing worktree for the session when one exists (same session, same branch, `Workspace.ensureWorktree`); otherwise it fetches (hooks off) and adds the worktree from `origin/<default_branch>`. `base_ref` is informational until [ADR-0039](../adr/0039-base-refs.md) B2.

Absent (or invalid) `__working_copy`: no `working_copy` in the payload, the M1 clone path (local mode).

**Lost machines (U-068).** The `input_request.kind` is a **new value `machine_lost`** (`MACHINE_LOST_KIND`), not `timeout`: the question isn't a timeout, and the card and filters need to tell them apart. **`input_request.kind = machine_lost`, added to the InputRequestKind enum + DB enum + web label by M2-T03.** Until then `create_input_request.kind` stays `InputRequestKindSchema`, and T06 (which now depends on T03) emits it.

`machine.lost {machine_id, reason, machine_name?, offline_ms?}` comes from the orchestrator (T20):
- `lease_expired`: the reaper, for a session whose `lease_expires_at` is past its expiry **plus the 2-minute grace** of [04 §4](04-scheduler.md#4--leases-and-fencing). The reaper selects only `assigned` / `running` / `waiting_external` sessions (lead decision 2026-10-27): a parked or queued session holds no lease worth reaping;
- `revoked`: the caller of `revokeMachine`, once per non-terminal session on that machine;
- `pinned_machine_offline`: the reaper, for a queued session pinned to a machine (a reopen pin, TD-088, or a `__machine_lost` mark: a queued session carrying the mark **is** pinned to `mark.machine_id`) that has been offline for `PINNED_MACHINE_OFFLINE_AFTER_MS` (900 000 ms; `CONDUCTOR_PIN_OFFLINE_MS` overrides it). `offline_ms` carries the threshold used. When the pinned machine has `revoked_at` set, the same pin SQL sends reason **`revoked`** instead (no waiting for the threshold): such a session can never continue there.

**apply stays pure and trusts the event.** The pin check is the reaper's SQL (T20). `SessionSnapshot` has no pin field, and apply never decides whether a session is pinned. `machine_name` is the display name; the question falls back to `machine_id`. Frozen semantics, implemented by T06 (this table wins over the task block):

| Snapshot | Event | Result |
|---|---|---|
| `done` / `failed` (terminal) | any | ignored `session_terminal` |
| `assigned` / `running` / `waiting_external` (a gate step is left), `machine_id` = the event's | any reason | applied (A) |
| same statuses, `machine_id` ≠ the event's | any reason (`lease_expired` / `revoked` / `pinned_machine_offline`) | ignored `machine_mismatch` |
| `queued` | `pinned_machine_offline` | applied (A), trusted |
| `queued` or `needs_input` with a `__machine_lost` mark for the event's machine | `revoked` | applied (B) |
| `queued`, no `__machine_lost` mark (a reopen-pinned session whose pinned machine was revoked; the reaper's pin SQL decided it) | `revoked` | applied (A), trusted; no kill; Cancel only |
| `needs_input` / `queued`, any other case | any | ignored `wrong_status` |

**(A) Applied:**
- the session enters the fallback human state (`fallbackHumanState`: `needs_input` when it is human, else the first human state; a definition with none fails the session, killing only as below); status → `needs_input`; ticket → `in_progress` when the session was `queued` (so the claim can't pick it); `return_to` = the current workflow state (the gate step's `from` when one was running; null when `workflow_state` is null); `agent_process_live = false`; **`machine_id` is kept** (for a queued session: the event's); no deadline (parked time doesn't count);
- `create_input_request {kind: machine_lost, question: machineLostQuestion(name, reason, offline_ms), return_to}`: `"<machine> stopped responding"`, `"<machine> was revoked"`, `"<machine> has been offline for <formatOfflineDuration(offline_ms)>"` (default 15 minutes);
- `context.__machine_lost` = `MachineLostMark {machine_id, machine_name, reason, state, at}` (`MACHINE_LOST_CONTEXT_KEY`, no migration);
- an answer the agent never ran on (`pending_answer`: a reopen message, an earlier Continue's answer, an answer whose start never began) is kept under `context.__machine_lost_answer` (`MACHINE_LOST_ANSWER_KEY`, a `PendingAnswer`), since entering the human state clears `pending_answer`. It is delivered at Continue (combined-answer rule below);
- for `lease_expired` and `pinned_machine_offline` when a process may still run (`assigned` / `running` / `waiting_external`): one `kill {reason: 'machine_lost'}` effect (`target_command_id` absent: every process of the session at or below the row's token). Its outbox row targets `machine:<machine_id>` and waits until the machine reconnects; outbox order per target delivers it before any later command. **No kill for `revoked`**: the machine can never reconnect, and see revoke below.

**(B) Revoked while already parked or waiting on the machine:** status → `needs_input` (ticket `in_progress` if it was `queued`), the mark's `reason` becomes `revoked`, and a new `create_input_request` with the `revoked` question (`return_to` unchanged). A parked (`needs_input`) session changes nothing else. A `queued` one (Continue requeued it into an agent or command state) is parked as in (A), with no kill, in the fallback human state: its `return_to` is the state it was requeued in, which is the first park's `return_to`. The wrapper closes the previous open request as superseded (`answer = '[superseded]'`, `answered_by = 'system'`) in the same transaction. No kill.

**Fencing (R5): one owner, the EngineService wrapper** (`orchestrator/src/engine/service.ts`). It already bumps `session.fencing_token = nextval('fencing_seq')` after apply and before writing the outbox rows: on a non-ignored `start_session` refusal and on gate-step changes ([EngineService wrapper](#engineservice-wrapper)). The re-claim bump stays in the claim (`gateway/claim.ts`). An applied (non-ignored) `machine.lost` joins the wrapper's list, so the kill row and every later command carry the new token. The old worker's late events are refused `stale_fencing_token` and killed (the `spend` exception as today). apply never changes `fencing_token`.

**Revoke and the outbox (R4).** `revokeMachine` (T09), in its transaction: set `revoked_at`; mark every `pending` / `sent` outbox row targeting `machine:<id>` `failed` (`last_error = 'machine_revoked'`), with no engine event, including fenced kills left by an earlier `lease_expired`; close the socket with `CLOSE_REVOKED`. Its caller (T20) then applies `machine.lost {reason: 'revoked'}` to each non-terminal session of the machine. Nothing is left pending for a machine that can't return. The gateway processes no frame from a connection it has started to close (revoke, replace, refusal), terminates a peer that hasn't answered the close within 1 s, and guards the heartbeat and session_event machine UPDATEs with `revoked_at IS NULL`; the claim share-locks the machine row, so a claim in flight serialises against revoke (M2-T09b).

**The human's options:**
- **`lease_expired` / `pinned_machine_offline`** (`machineLostCanContinue` true):
  - **"Continue on <machine>"**: the human state's `$return_to` transition (`conductor`'s `answer`), shown with `machineLostContinueTitle(name)` while the open request's kind is `machine_lost` (card derivation). Taking it re-enters `return_to`; with no live process apply requeues (status `queued`, ticket `ready`, `machine_id` null), keeping the mark. The same holds for **any** human move or answer out of the park into an agent or command state (or a move with `requires`): the pin is kept. The claim (T16) offers a queued session carrying the mark **only to `mark.machine_id`** (a hard filter, like the [reopen pin](04-scheduler.md#2--claim-query-ticket-side)); `session.assigned` then re-emits the state's `start_session` with `resume_claude_session_id` (and its `__working_copy`). A `return_to` of null (a never-started reopened session) enters `def.start` at Continue (requeued there, so the claim re-emits its start).
  - **The mark is cleared** on the next matching `session.started`; at a `session.assigned` whose re-emit has no `start_session` (a command, a check phase, an event or human state: no `started` will come); on a human move or answer into a state that needs no machine (event, human, terminal); and when the session becomes terminal (`done` / `failed` / `lost`), with the kept answer, so a reopen (which copies the context) never inherits a stale pin.
  - **Combined answer.** When an answer was kept (above) and the Continue (or answer) goes into an agent state, the delivered answer (the `pending_answer`, so the next `start_session.prompt` is it on a resume, and contains it otherwise) is `"Your earlier message (sent before <machine> was lost):\n<earlier>\n\nOn continuing:\n<text>"` (`combineLostAnswer`), the earlier text first. With no text (a Continue without one) it is the earlier text alone. A move into anything else drops the kept answer.
  - **Cancel**: the existing operator action.
- **`revoked`** (`machineLostCanContinue` false): **Cancel only.** The card shows no transitions. apply ignores any `human.transition` while the mark's reason is `revoked` (`transition_not_allowed`) and any `input.provided` (`wrong_status`).
- In every case there is no automatic requeue to another machine (U-011/U-012 stay open: the worktree and the transcript are on the lost machine).

**What each consumer builds from this** (for the interface review):
- **T04** (daemon auth): `daemonAuthHeaderValue` on the upgrade when enrolled; `register.protocol_version = PROTOCOL_VERSION`; on 401 or 4003 / 4001 stop and exit non-zero; on 4005 log the update hint.
- **T06** (engine): `requiredCapabilities` in `machines/required.ts` (replace the stub, or delegate to `workflow/capabilities.ts`); `machine.lost` in `apply.ts` (replace the two `// M2-T06` stub cases) per the table above, using `MACHINE_LOST_KIND` once T03 has widened the enum; the `revoked` refusals of `human.transition` / `input.provided`.
- **T09** (credentials, register, revoke): `parseDaemonAuthHeader`, 401 at the upgrade, `CLOSE_PROTOCOL` for v1 in password mode; `machine_repo` from `InventoryRepo`; `machine_capability (machine_id, key)` from `capabilityKeys`; `revokeMachine` fails the machine's pending / sent outbox rows and closes with `CLOSE_REVOKED`.
- **T10** (scanner): emit `inventory` with `InventoryRepoSchema` / `CapabilitySchema` values only (names and versions, never secrets; no repo-scoped skills or agents for a repo whose remote is null) and its `hash`; emit `alert` with a `seq`.
- **T13** (working copies): honour `start_session.working_copy` after re-checking it against the inventory; reuse the session's existing worktree, else base it on `origin/<default_branch>`.
- **T16** (ingest, claim): replace a machine's rows on each `inventory`; dedupe `alert` on seq; claim filters on `remote` and the matching rule above; `missingCapabilities(…, ticket.repo)` for the badge; the `__machine_lost` pin; write `__working_copy` into the session context in the claim transaction.
- **T20** (reaper, revoke wiring): emit `machine.lost` with `machine_name` (and `offline_ms` for `pinned_machine_offline`) after the 2-minute grace; the pin SQL; `PINNED_MACHINE_OFFLINE_AFTER_MS` / `CONDUCTOR_PIN_OFFLINE_MS`; add `machine.lost` to the wrapper's fencing-bump list in `engine/service.ts`; call `machine.lost revoked` after `revokeMachine`.

## Daemon auto-update

[ADR-0021](../adr/0021-daemon-auto-update.md); tasks M2-T18 (launcher, wake), T18b (these contracts), T18c (daemon), T18d (orchestrator), T18e (web). Additive: daemons that don't know it ignore `update_available` (unknown frame types are logged and dropped) and keep the 4005 hint.

| Seam | File | Producer → consumers |
|---|---|---|
| `update_available {version, file, sha256, size}` (`UpdateAvailablePayloadSchema`, direct frame, not an `OrchestratorCommand`) | `shared/src/protocol/ws.ts` | T18d gateway → MR-T14 daemon |
| `heartbeat.draining?: {reason: 'update', version}` | `shared/src/protocol/ws.ts` | MR-T14 → T18d (`machine.status`) |
| `alert {kind: 'update_failed', version, stage, error, at}` (`UpdateFailedAlertPayloadSchema`; `AlertPayloadSchema` is now a union on `kind` with `git_tamper`) | `shared/src/protocol/ws.ts` | MR-T14 → T18d ingest → T18e |
| `LatestDaemonSchema` (`GET API_PATHS.daemonDownload(LATEST_DAEMON_FILE)`), `DAEMON_TARBALL_RE`, `DAEMON_TARGET_RE`, `DAEMON_VERSION_RE`, `DAEMON_TARBALL_MAX_BYTES` (100 MB), `daemonTarballMatches`, `UpdateFailedStageSchema`, `UPDATE_FAILED_ERROR_MAX` 500, `EXIT_RESTART_FOR_UPDATE` 75, `UPDATE_*` limits | `shared/src/machines/update.ts` | T18d route → MR-T14 (4005 path); T18 units |

**Build names** (ADR-0021 §1 as amended for ADR-0026): `file` matches `^conductor-daemon-[0-9A-Za-z._+-]{1,128}\.tgz$` and is either `conductor-daemon-<version>.tgz` or `conductor-daemon-<version>-<target>.tgz`, where `<target>` is a lower-case Rust triple (`^[0-9a-z_]+(-[0-9a-z_]+){1,3}$`). The check is a zod `.refine`, so the generated Rust types don't carry it (TD-196): the Rust updater calls its own port of `daemonTarballMatches`. `latest.json` keeps the one-build body; the daemon adds `?os=<register.os>&arch=<register.arch>`, and with no query the server returns its only build (T18d / MR-T15).

**Served builds** (MR-T15, `orchestrator/src/distribution.ts`): the orchestrator serves `conductor-daemon-<version>-<target>.tgz` + `.sha256` for `DAEMON_TARGETS` = `aarch64-apple-darwin`, `x86_64-apple-darwin`, `x86_64-unknown-linux-gnu`, `aarch64-unknown-linux-gnu`, `x86_64-pc-windows-msvc`, all of one version (`findDaemonDist`; names are parsed by the target suffix, since a version may contain `-`). `targetFor(register.os, register.arch)` maps the Node names both daemons send (`darwin`/`linux`/`win32`, `x64`/`arm64`) to a target, or null, for `update_available` and `latest.json`. The install templates get `@@PUBLIC_URL@@`, `@@VERSION@@` and, per target, `@@FILE_<T>@@` / `@@SHA256_<T>@@` (`<T>` = the target upper-cased, `-` → `_`; empty when that target has no build). `install.sh` picks by `uname -s`/`-m` (a Rosetta shell gets the arm64 build) and runs the new binary's `--version` before `current` moves; `install.ps1` takes the Windows build (503 when there is none). Neither checks for Node. Inside a tarball: `bin/conductor-daemon` (Windows: `bin/conductor-daemon.exe` and a one-line `bin/conductor-daemon.cmd`), `assets/conductor-launch.sh`, `VERSION`. The binary's version is `<workspace version>+<sha>`, the sha baked in at build time (`config.rs` `pick_build_sha`: a runtime `CONDUCTOR_BUILD_SHA` still wins).

**`config.json`** gains `"auto_update": false` when switched off (`conductor-daemon config auto-update on|off`, Rust only); on is the default and is never written, so a TS-written file is unchanged. `config show` prints `auto_update`.

**Not yet stored**: `machine_alert.kind` (and `MachineAlertKindSchema`) is still only `git_tamper`, so the gateway drops an `update_failed` alert (its seq not consumed) until T18d adds the kind (a migration) and removes that check in `ingestAlert`. The TS daemon logs and ignores `update_available` (it never self-updates; ADR-0026 freeze).

**On disk** (`<root>` = `~/.conductor`): `daemon/<version>/`, `daemon/current` → one of them (POSIX: a relative symlink `<version>`, always swapped by renaming a temp symlink over it; Windows: a junction, removed and re-made, so not atomic: TD-218), `daemon/trial` (exactly `from=<v>\nto=<v>\nattempts=<n>\n`, written by the daemon via tmp + rename: an update not yet committed), `daemon/bad-versions` (one version per line, appended by the launcher on a rollback; never acted on again), `daemon/bad-versions.reported` (the daemon's own list of the bad versions it has sent `alert update_failed {stage: trial}` for, so each is reported once), `daemon/.staging-<random>/` (a download in progress; removed on failure and swept at startup), `bin/conductor-launch` (the version-independent launcher the units run; `bin\conductor-launch.ps1` on Windows). Every version read from these files is checked against `DAEMON_VERSION_RE` (and is not `.`/`..`) before it is used in a path, by the daemon and by both launchers.

**The Rust updater (MR-T14a, `crates/conductor-daemon/src/update/`, wired in `daemon/updating.rs`)**:
- **Stage** (`update::stage`): `GET <http origin>/downloads/<file>` with redirects off, https or a loopback http host only; exactly `size` bytes with the announced SHA-256 (else `verify`); the tarball is read twice, every entry checked first (no absolute path, `..`, drive, backslash, link leaving the archive, device or fifo; else `unpack`) and only then unpacked; `bin/conductor-daemon[.exe] --version` (run without `CONDUCTOR_BUILD_SHA`, 30 s) must print `version`; then renamed to `daemon/<version>`. An existing `daemon/<version>` that passes the `--version` check is reused without a download.
- **Policy** (`update::policy`): `update_available` is ignored (logged once) when `config.json` has `"auto_update": false`, when it names the running version, a `bad-versions` entry, or the update already in progress, during the 1 h cooldown after a failed attempt (a failed stage counts like an abandoned drain), and after 3 failed attempts for that version until a restart or a newer build. The config file is re-read each time, so `config auto-update on|off` needs no restart.
- **Switch gate** (`update::switch::can_switch`): only with `CONDUCTOR_SUPERVISED` set (by the units; `run` passes it) **and** an installed launcher containing the line `# conductor-launch: trial-v1`. Otherwise the build is staged only and the daemon logs once why (`restart conductor-daemon to use it`, or `re-run the install command to enable automatic updates` for M2-T18's plain launcher, which can't roll back).
- **Drain and idle**: while draining, `request_work` is never sent and every heartbeat carries `draining`; commands are still honoured. Idle = no starting session, no work assignment held, no `run_cmd`/`run_action`, no assistant job, and every live agent parked (its turn ended with `ask_pending`: `ask_user` or `no_outcome`). Checked whenever work ends and every 5 s. Idle → write `trial`, repoint `current`, `run` exits 75. A switch that fails ends the drain with `alert {stage: unpack}`.
- **Trial start**: a daemon whose version is `trial.to` arms a 120 s timer when its socket opens; no `registered` by then → exit 75 (a failed start for the launcher). On `registered` it deletes `trial` (the commit) and removes every version dir except `current`, `trial.from` and anything a remaining `trial` names.
- **Launchers** (`assets/conductor-launch.sh`, `.ps1`): before each start, if `trial` exists, `attempts += 1`; past `UPDATE_MAX_TRIAL_ATTEMPTS` (the third start) and with `daemon/<from>` present, `current` goes back to `from`, `to` is appended to `bad-versions` and `trial` is deleted; a `trial` with an unsafe version is deleted. The sh launcher in the tarball is `crates/conductor-daemon/assets/conductor-launch.sh`, byte for byte.

**Exit codes**: 75 `EXIT_RESTART_FOR_UPDATE` (restart me; both units restart on it), 78 `EXIT_FATAL_AUTH` (don't restart, M2-T18).

**Service units** (M2-T18, `daemon/src/commands/service.ts`): `conductor-daemon service install|uninstall|restart|status`, as the user, never sudo. macOS: launch agent `~/Library/LaunchAgents/com.conductor.daemon.plist` in `gui/<uid>` (`RunAtLoad`, `KeepAlive {SuccessfulExit: false}`, `ThrottleInterval` 30, stdout and stderr to `<root>/logs/daemon.log`). Linux: `~/.config/systemd/user/conductor-daemon.service` (`Restart=on-failure`, `RestartPreventExitStatus=78`; logs in the journal). Both run `<root>/bin/conductor-launch` and set `CONDUCTOR_SUPERVISED=launchd|systemd`, `CONDUCTOR_ROOT`, `CONDUCTOR_NODE` and `PATH`. `install` rewrites a file only when its bytes differ, so a second run changes nothing.
- **Launcher, one source**: `crates/conductor-daemon/assets/conductor-launch.sh` ships in the tarball as `./assets/conductor-launch.sh`. `service install` writes the copy built into the binary, and `install.sh` copies it from the unpacked version, so both write the same bytes (asserted by `install-script.test.ts`, which reads the crate's asset). It finds `<root>` from its own path, so the bytes don't depend on the root.
- **Node is pinned at `service install`** (the tarball's `bin/conductor-daemon` runs `${CONDUCTOR_NODE:-node}`). `service install` resolves an absolute node: `CONDUCTOR_NODE` if set, else the `node` on PATH when it is the node running the command (a stable path such as `/opt/homebrew/bin/node`, not the Cellar one), else `process.execPath`. It refuses anything below Node 22 with the `CONDUCTOR_NODE=$(nvm which 22)` hint. The unit's `PATH` is that node's directory followed by the installing shell's PATH (launchd's own PATH has no Homebrew, `claude` or `gh`). Changing Node or moving tools means re-running `service install`. `run` on Node < 22 only warns.
- **Rust daemon (MR-T13a, ADR-0026)**: `crates/conductor-daemon/src/commands/service.rs` writes the same units **without** `CONDUCTOR_NODE`, and its `service install` has no Node check: the binary needs no Node. The unit's `PATH` is the installing shell's absolute PATH entries, deduplicated. The launcher is `crates/conductor-daemon/assets/conductor-launch.sh`, byte-identical to the TS asset (asserted by `service/tests.rs`). Units written by the TS daemon still set `CONDUCTOR_NODE`; the Rust daemon ignores it, and its `service install` rewrites them without it. On Windows `service` drives a Scheduled Task (below). `conductor-daemon run` (MR-T13b, `commands/run.rs`) exits 78 on a fatal close and, under `CONDUCTOR_SUPERVISED=launchd`, boots its own job out first; the first of a fatal close and a stop signal decides the code, so the bootout's SIGTERM never turns 78 into 0.
- **Windows Scheduled Task (MR-T13c, Rust only)**: a per-user task `conductor-daemon` (LogonTrigger and InteractiveToken principal for the user's SID, `LeastPrivilege`, `ExecutionTimeLimit PT0S`, `MultipleInstancesPolicy IgnoreNew`, no battery stops), registered with `schtasks /Create /XML <root>\service\conductor-daemon.task.xml /F` (the definition is written UTF-16LE with a BOM and only when its bytes differ). Its action is `powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -WindowStyle Hidden -File "<root>\bin\conductor-launch.ps1"` (a brief console flash at logon; a GPO `AllSigned`/`Restricted` policy overrides `Bypass`). The launcher, `crates/conductor-daemon/assets/conductor-launch.ps1`, is U-114's stopgap: it sets `CONDUCTOR_SUPERVISED=schtasks` and `CONDUCTOR_ROOT` (PATH is the user's own), resolves `daemon\current\bin\conductor-daemon.exe` before every start, and holds the restart policy Task Scheduler can't express: 0 and 78 stop, 75 and crashes restart after 5 s. Logs: `<root>\logs\daemon.log` (stderr; the previous run in `daemon.log.1`), `daemon.out.log`, `launcher.log`; the daemon's pid in `logs\daemon.pid`. `restart` is `schtasks /End` then `/Run`; `uninstall` is `/End` then `/Delete /F`; after `/End`, a `conductor-daemon.exe` still running under that pid is killed. `status` reads `(Get-ScheduledTask).State` (not localized) and exits 0 only when `Running`. Stopping the task (and logoff) is TerminateProcess: no console event reaches the daemon (U-108), so it is never graceful (TD-190). Trial and rollback run in the `.ps1` before every start (MR-T14a; U-114: the `.ps1` is the Windows launcher).
- **78 doesn't restart**: systemd through `RestartPreventExitStatus`. launchd can't exclude one exit status, so on a fatal close under `CONDUCTOR_SUPERVISED=launchd` the daemon runs `launchctl bootout gui/<uid>/com.conductor.daemon` before exiting 78. The agent loads again at the next login (one attempt per login), and `ThrottleInterval` is the floor if the bootout fails. Close 4005 (protocol too old) also exits 78: restarting can't fix it, and the `install.sh` upgrade runs `service restart`.

**Limits**: drain ≤ 6 h, then resume work, alert `drain_timeout`, 1 h cooldown, at most 3 drains per version; trial = 2 starts, and a start fails if the new version crashes or reaches the server without `registered` in 120 s (no network doesn't count).

## Permission prompts

[ADR-0023](../adr/0023-permission-prompts-through-conductor.md); tasks M2-T29 (these contracts), T29b (daemon), T29c (orchestrator), T29d (web). Frozen by M2-T29; later tasks report a needed change to the lead. Every addition is additive: an older daemon never sends `permission_request`, so an older orchestrator never has to answer one, and every new card / DTO field is optional (absent ≡ none), so pre-T29 cards and frames parse unchanged. Wire shapes are in [03](03-protocols.md#daemon--orchestrator-websocket); failure handling in [08](08-failure-modes.md#permission-prompt-held-open).

**The request (daemon → orchestrator).**
- Claude calls the `mcp__conductor__permission` tool only when auto mode would still ask (deny rules such as `Bash(git push:*)` are evaluated first and never reach it, ADR-0023 §4). The daemon gives the held call a fresh `request_id` (uuid) and sends `permission_request` on the session's envelope with its current fencing token.
- **Durable**: `seq` is required; the daemon buffers and replays it like a `session_event`, and the gateway dedupes it on `(machine_id, seq)` with the same `machine.last_seq` guard ([Daemon seq dedupe](#daemon-seq-dedupe)). A stale fencing token is refused and killed like any other session message. `payload.session_id` must equal the envelope's.
- `request_id` is the idempotency key: the orchestrator stores the row with `INSERT … ON CONFLICT (id) DO NOTHING`, so a replay or a duplicate changes nothing.
- `tool` is Claude's `tool_name` (1–200 chars); `input` the tool input, a JSON object of at most **64 KiB of UTF-8 JSON** (`PERMISSION_INPUT_MAX_BYTES`). Why 64 KiB: a human can't review more than that on a card, a stored row stays small, and it is far under the 4 MB frame limit. Over the bound, the daemon denies the call itself with "input too large to review (N bytes)" and sends nothing.
- `suggestions` are Claude's `permission_suggestions` (PermissionUpdate objects), at most 10 and 16 KiB; over that the daemon drops them. They are shown, never applied: "Allow always" records conductor's own exact rule. `tool_use_id` is informational.
- `expires_at` = when the daemon will deny the call itself: now + `DEFAULT_PERMISSION_TIMEOUT_MS` (30 min; per machine later, ADR-0023 §2).
- The orchestrator accepts a request only while the session is `running` an agent state with a live process (outside a gate step). Otherwise it stores it already `denied` (`decided_by: null`, message "the session is not running an agent") and sends the deny back on the same socket at once (no outbox row, U-099); the card does not change.

**The sub-status `needs_permission`.**
- Not a `session.status` value and not an FSM transition: the session stays `running` in its state, its column and `status` don't change, no engine event is applied, `return_to` and counters are untouched. Wall time and the lease keep running (the held call keeps the turn open; the 30-min timeout bounds it).
- Derived from the session's `pending` permission requests (T29c: the `permission_request` table keyed by `request_id`, [02](02-data-model.md#permission_request)). Every card derivation (the engine wrapper's `card.upserted`, `GET /api/board`, `GET /api/sessions/:id`) adds it (`withPermission`, `orchestrator/src/permissions/store.ts`). `BoardCard.sub_status = 'needs_permission'` and `BoardCard.permission` = the **oldest** pending request (`request_id`, `tool`, `permissionSummary(input)`, `expires_at`) plus `pending_count`, set exactly when at least one is pending; both absent otherwise.
- Set and cleared in the **same transaction** as the request / decision / expiry write, with a `card.upserted` board event (no new SSE type).
- `BoardCard.sub_status` reads an unknown value as null, so a newer server can add sub-statuses without breaking an older UI.

**The decision (REST → orchestrator → daemon).**
- `POST /api/permission-requests/:id/decision` `{behavior, scope, message?}`, by the **ticket owner** (404 for another account's or an unknown id). The buttons: **Allow once** `{allow, once}`, **Allow always** `{allow, always}`, **Deny** `{deny, once, message?}`. A deny is never `always` (400). `message` is trimmed, 1–2 000 chars.
- In one transaction: lock the request row; record the decision (`status` `allowed` / `denied`, `decided_by` = the user id, `resolved_at`); for `always`, record `always_rule` as an exact allow rule (appended once to the ticket's `session_allow` until M2-T28c, then on the machine override, ADR-0023 §2); store a fresh `command_id` on the row (`decision_command_id`); update the card. After COMMIT, send the `permission_decision` frame built by `permissionDecisionCommand` (target the session's machine, the session's current fencing token, `rule` = the recorded rule for `always`) on the machine's live socket (see **No outbox kind** below). Reply 200 with the decided `PermissionRequestDto`.
- **Idempotent on the request id**: the same `{behavior, scope}` again → 200 with the stored decision and no second command. A different decision, or any decision on an `expired` request → 409 `permission_not_pending`. `scope: always` on a request whose `always_rule` is null → 400 `bad_request`.
- `PermissionRequestDto.always_rule` is computed by the orchestrator (T29c) from `tool` + `input`: the exact rule "Allow always" would record (e.g. `Bash(pnpm exec tsc -b)`); null when the input has no exact rule, and the UI then offers only Allow once and Deny. Computed once, when the request is stored.
- **`always_rule` grammar** (U-100, Ben 2026-10-28; `alwaysRuleFor`, `orchestrator/src/permissions/rule.ts`):
  - `Bash`: `Bash(<exact command>)`; null if the command is blank, contains `)`, a newline (`\n` / `\r`) or `*`, or ends in `:*`. (`*` is a wildcard in Claude Code Bash rules, so a rule containing it would match more than this call; T29c added it to U-100's list for that reason.)
  - MCP tools (`mcp__*`): the bare tool name.
  - `Edit`, `MultiEdit` (`file_path`), `NotebookEdit` (`notebook_path`): `Edit(//<exact absolute path>)`; `Write`: `Write(//<exact absolute path>)` (Claude Code reads `/p` as relative to the settings source and `//p` as absolute); null if the path isn't absolute (doesn't start with `/`) or contains `)`, a newline or a gitignore glob character (`*`, `?`, `[`, `]`, `\`).
  - `WebFetch`: `WebFetch(domain:<host>)` from the URL's hostname; null if the URL doesn't parse or has no host.
  - Anything else, or a rule longer than `PERMISSION_RULE_MAX`: null.
- **No outbox kind** (Ben, 2026-10-28, U-099): after the transaction commits, the route sends `permission_decision` directly on the machine's live WebSocket. There is no outbox row, no migration and no engine Effect, so the "one Effect per outbox kind" invariant is untouched. Delivery is best effort: if the machine isn't connected, or the daemon doesn't ack, the decision stays stored and the request expires into a deny (the same path as a daemon restart, 08 §Permission prompt held open). The daemon still dedupes on `command_id` and acks. TD-179 tracks the durability gap.
- **Daemon**: resolves the held call whose `request_id` matches, at most once, and acks `accepted: true`. A second decision for a request it already resolved (another `command_id`) is acked `accepted: true` and ignored. A request it doesn't hold (timed out, process gone, daemon restarted) is refused `unknown_permission_request`; the orchestrator matches the ack to the request by `decision_command_id`, marks the request `expired` (`agent_gone`) if it is still pending (with the card), and does not retry. A request already decided keeps its decision; the session's output log gets a `debug` line saying the decision arrived after the agent stopped waiting.
- **What Claude gets** (the permission-prompt-tool reply, T29b): allow → `{behavior: 'allow', updatedInput: <the request's input>}`, plus, for `always` with `rule`, `updatedPermissions: [{type: 'addRules', rules: [<rule as {toolName, ruleContent}>], behavior: 'allow', destination: 'session'}]` so this process doesn't ask again; deny → `{behavior: 'deny', message}`: "Permission denied by a human on the board: <note>" with the human's note, or "Permission denied by a human on the board." without one (the decision frame names no user, so the daemon can't name them; T29b).

**Expiry** (`status: expired`, `expired_reason`), in the transaction that observes it, with the card update:
- `timeout`: `expires_at` passed. The daemon has already denied the call ("no human answered within 30 min"; the agent can then `ask_user`). The orchestrator's sweep marks it at `expires_at` (its own clock; a decision posted in between reaches the daemon after its own timeout and is refused `unknown_permission_request`, which ends the same way).
- `agent_gone`: an `exit` for the session's agent process (including the daemon's `exit {signal: 'daemon_restart'}` after a restart, [03 §Delivery](03-protocols.md#delivery-guarantees)), or the daemon refused the decision.
- T29c applies `agent_gone` / `session_moved` in the EngineService wrapper's transaction (`expireOnApply`): after any applied event, a session that is no longer `running` with a live process outside a gate step, in the same state with the same `agent_command_id`, expires its pending requests (`agent_gone` for an `agent.exited` or a process that went away while the session stayed put, `session_moved` otherwise). The `timeout` sweep runs with the engine's timeout sweep (`sweepPermissionTimeouts`).
- `session_moved`: the session leaves the agent state, parks (`needs_input`), fails, finishes or is cancelled while the request is pending.

**Versioning.** No `PROTOCOL_VERSION` bump. A daemon that sends `permission_request` to a pre-T29 orchestrator gets `protocol_error {code: 'invalid_message', ref_msg_id: <its msg_id>}`; the daemon then denies the held call at once ("this conductor server can't show permission prompts"), so an old server never strands an agent for 30 min. Daemons before T29b never send it; a T29 daemon without T29b refuses any decision `unknown_permission_request`.

**What each consumer builds from this:**
- **T29b** (daemon): the `permission` tool; `permission_request` with a durable `seq`; the 64 KiB check and local deny; the timeout at `expires_at`; resolve on `permission_decision`, ack rules above; deny every held call on shutdown and on a `protocol_error` naming the request. Also deny when the agent process exits while a call is held. The CLI's `--help` is probed once at daemon start; a CLI without `--permission-prompts` or `auto` mode gets the pre-ADR-0023 flags (ADR-0006 §Notes).
- **T29c** (orchestrator): storage keyed by `request_id` (plus `ticket.session_allow`; not yet fed into the next `start_session`, which would need daemon changes); the gateway's `permission_request` handler (dedupe, running check, card); the two routes; `always_rule`; the direct send on the live socket (no outbox, U-099); the expiry paths; `unknown_permission_request` acks.
- **T29d** (web): the card badge from `sub_status` / `permission`; the drawer list from the GET route; the three buttons (Allow always hidden when `always_rule` is null), the deny note box.

No response ever carries an endpoint (NFR-2).

**Enqueue** (FR-4, `orchestrator/src/push/enqueue.ts`): in the EngineService wrapper's transaction, right after it inserts an `input_request` (`create_input_request`; under an ADR-0037 P6 notify policy only when its `notify_decision` is `push`, keyed by the coalesce bucket when the policy has one), one outbox row per user of the ticket's account who has a subscription: `kind = 'push_needs_input'`, `target = 'user:<user_id>'`, `account_id` = the ticket's, `idempotency_key` = the input request id, no fencing token, `INSERT … ON CONFLICT (target, idempotency_key) DO NOTHING` (`outbox_push_idem_idx`). Payload `{ticket_id, input_request_id, notification, delivered: []}`; the notification is rendered here. `push_needs_input` is not an engine Effect (`NON_EFFECT_OUTBOX_KINDS`; `CommandKindSchema` is every other kind, the ones a daemon can ack or refuse) and has no WS message: `commandEnvelopeForOutboxRow` throws for it, and the machine dispatcher only picks `machine:` targets.

**Transitions**: the wrapper's `state_entered` with `notify` ([05 §Notify](05-workflow-engine.md#notify)) enqueues `kind = 'push_transition'` rows the same way (`enqueueTransitionPush`, one per subscribed user of the account), `idempotency_key = 'transition:<state.entered event id>'`, payload `{ticket_id, event_id, notification, delivered: []}`. It can leave out one user (`excludeUserId`) but has none to leave out today: `human.transition` names no user (`actor: 'ui'`), so the person who took a move gets its push too. Their focused tab skips the in-tab one. `push_transition` is in `NON_EFFECT_OUTBOX_KINDS` and `PUSH_OUTBOX_KINDS`, and `commandEnvelopeForOutboxRow` throws for it.

**Permission prompts** (UXR-32): the gateway's `permission_request` handler, in the transaction that stores a **pending** request for a session running its agent ([§Permission prompts](#permission-prompts)), enqueues `kind = 'push_needs_input'` rows the same way (`enqueuePermissionPush`, one per subscribed user of the account) when push is on (`EngineService.pushEnabled`), then wakes the push dispatcher (`pushWritten`). `idempotency_key = 'permission:<request id>'`, payload `{ticket_id, permission_request_id, notification, delivered: []}`. A request_id seen before and a request denied by conductor (no agent running) enqueue nothing. Same kind, so no new enum value and the same dispatcher.

**Notification** (FR-5, `push/payload.ts`): `{title, body, url, tag}` = the ticket title, `<agent>: <question>`, `/#/?ticket=<ticket_id>`, the input request id. A transition's (`transitionPayload`): the ticket title, `<transition title>: <from column> → <to column>` (clipped to 120), the same url, `transition:<state.entered event id>`. No reason text. A permission prompt's (`permissionPayload`): the ticket title, `<state>: wants to run <tool>: <summary>` (the card's `permissionSummary`, clipped to 120), the same url, `permission:<request id>`. The agent name is the state that asked (the request's `return_to`, else the session's state). The title and question are clipped to 120 code points with `…`. Nothing else: no repo, branch, machine, answer or secret.

**Send** (`push/dispatcher.ts`, its own worker loop, 1 s poll, woken after a push enqueue; a slow push service only delays pushes, NFR-1): each due `push_needs_input` or `push_transition` row (`PUSH_OUTBOX_KINDS`) in its own transaction with `FOR UPDATE SKIP LOCKED`. It sends (`web-push`, pinned; TTL 3600 s, `Urgency: high`, 10 s socket timeout) to each of the target user's subscriptions in the row's account not yet in `payload.delivered`, and books each result on the subscription:
- accepted: added to `delivered`; `last_ok_at = now`, `failures = 0`;
- 404 / 410: the subscription is deleted;
- anything else: `failures + 1`; the 5th consecutive failure deletes it.

Nothing left to send → `acked` (and `payload.notification` nulled). Otherwise the row stays `pending`, `attempts + 1`, `next_attempt_at` after the dispatcher's backoff (5, 10, 20, 40, then 60 s), `last_error` = the last failure. A row older than the TTL (1 h) becomes `failed`, `last_error = 'expired'`, unsent. `delivered` makes a retry send only to the subscriptions that failed; a crash between a send and its COMMIT can resend that one once, and the browser replaces the duplicate by its `tag`.

**Web** (UX-16, `packages/web`): conductor is an installable PWA (`public/manifest.webmanifest`, `display: standalone`, PNG icons in `public/icons/`, linked from `index.html` with an `apple-touch-icon`); iOS delivers Web Push only to a Home Screen app. `public/sw.js` (served by `web-static.ts` with `no-cache`, scope `/`) shows the notification above (`tag` = the input request id, icon, `data.url`) and, on a click, focuses an open conductor window and posts it `{type: 'conductor:open', url}`, else opens `url`. It has no fetch handler and caches nothing. `notify/push.ts` drives the account menu's **This device: on/off**: on = permission (from the click only), register `sw.js`, `pushManager.subscribe` with the VAPID key, `POST /api/push/subscriptions`; off = `unsubscribe()`, then `DELETE`; **Send test** = `POST /api/push/test`, which shows the count, or the first reason when a device failed. On menu open, a granted device that already has a subscription resyncs the server. If the subscription's `applicationServerKey` differs from the server's key (the keys were rotated), it is unsubscribed and the menu reads `off`. Otherwise it is POSTed again (an idempotent upsert), so a subscription the server dropped after failures comes back. **This device: on** also replaces an old-key subscription before subscribing. A browser without push keeps UX-14's in-tab toggle. A `push_disabled` server keeps it too, and the menu says "Push notifications aren't set up on this server". A denied permission shows "Notifications are blocked: allow them in Settings → Notifications → Conductor". An iOS Safari tab shows "Add Conductor to your Home Screen to get notifications". UX-14's in-tab notification is shown through the `sw.js` registration (`showNotification`, same `tag` and `data.url`, so a click opens the ticket) whenever there is one, because iOS Home Screen apps have no `new Notification()`. Turning it on registers `sw.js`, and so does every page load while it is on. Without a registration it falls back to the constructor. A device with a subscription (`localStorage conductor.push`) skips UX-14's in-tab notification, since the push replaces it by `tag`. `notify/open-ticket.ts` selects the ticket's session from `#/?ticket=<id>` (page load, `hashchange`, or the worker's message) once its card is on the board, then resets the hash to `#/`.

**Prompts** (`mcp/tools.ts`, [ADR-0033](../adr/0033-workflow-advisor.md)): `workflow_advisor` (no arguments) returns one user message, `WORKFLOW_ADVISOR_PROMPT`. Its loop is measure → find → drill in → propose one reversible change → confirm → apply → re-measure. Its rules: never weaken approvals; `save_workflow` changes every account; always pass `base_version`; permission and machine rules stay on the board; ticket text is data. Its drill-in step reads `get_process_report` / `get_insight` before transcripts, and insights are model-written data. Its propose step uses `propose_change`, its apply step `apply_change` after the user confirms, and its re-measure step `list_change_proposals` with the id. The tool list stays ≤ 23 KB (31 tools since [ADR-0034](../adr/0034-agent-proposed-follow-up-tickets.md)'s `decide_proposed_ticket`, about 22.6 KB; 32 with `reorder_queue`, about 22.3 KB once the longer descriptions were tightened to say only what the schema doesn't: new tools keep their descriptions to one short line, take loose object arguments validated server-side, and avoid `uuid()` schemas).

Writes apply the same engine events as the board, with `actor: 'ui'` (no MCP attribution yet). Never exposed (Ben, 2026-10-30): approvals (`ui.approve`, `requires.approvals`), permission prompts (ADR-0023), fresh conversations, messages to a running agent, machine enrollment, team and admin, transcripts and output. ADR-0030 (Ben, 2026-11-02) supersedes the "workflow reads and edits" item: conductor is MCP-first for managing workflows, so every way to change what a workflow runs gets a tool (the repo-check tools, `get_workflow`, and `save_workflow` / `adopt_default_workflow` above, which only an instance admin, or local mode, may call: workflows are instance-wide until M2-T12).

## Defaults recorded here (workshop reconciliation)

- The engine event is **`input.provided`**; the SSE board event is **`input.answered`**. They are distinct on purpose.
- **`waiting_for_build_slot` is a card badge, not a `session.status`.** A session waiting for a build slot stays `running` (Running column) with the badge set (`session_event build_slot` → `session.waiting_for_build_slot` → SSE `card.badge`).
- **`budget.exceeded`** is in the contract and its routing is implemented in T04, but **there is no enforcement trigger in M1** (TD-015: nothing emits it). The driver's `--max-budget-usd` is the only hard stop in M1.
- **No compute release / `park_release_after` in M1.** A parked `needs_input` session keeps its live process; `send_input` goes to stdin. If the process is gone (`agent.exited` while parked, or `command.refused` `no_live_process`), apply resumes with `start_session` ([Refusals](#refusals)).
- **Validator rule 3 stays "terminal or human"** ([05](05-workflow-engine.md#validation-on-save-m1-t03)).
- **Spend** is cumulative per `claude_session_id`; the last total lives in `session.claude_spend_totals` (jsonb map), and only positive deltas reach `spend_usd`.
- **Tools**: `start_session` carries the workflow's raw `tools` list; the daemon (T05) maps it to the ADR-0005 `ToolPolicy` with `resolveToolPolicy` ([Tools](#tools)).
- **Claude session id**: new sessions get it pre-assigned by the daemon (`resume_claude_session_id: null`); the orchestrator learns it from `session_event claude_session_id`.
- `base_ref` is `HEAD` of the shared clone in M1. The output tail for `cmd_exit` / `attach: output` is 16 KB.
- An unclaimed ticket (no session) shows in Queued: `columnFor(null) = 'queued'`, `BoardCard.session_id = null`.
- `ticket.repo_allow_machines` is kept as a nullable `text[]` (null = any machine) ([U-009](../tracking/UNKNOWNS.md)).

## Conventions

- Wire and DB names are snake_case. The ADR-0005 driver contract is camelCase (it's in-process); the daemon snake_cases when forwarding.
- DB row types follow node-postgres defaults (`bigint`/`numeric` → string, `timestamptz` → Date). Engine and API shapes use numbers and ISO-8601 strings.
- Workflow definitions are parsed strictly: unknown keys are errors.
