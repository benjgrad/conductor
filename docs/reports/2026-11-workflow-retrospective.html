1 · Executive summary

Across 152 tickets on this repo, tickets spent 637 hours in workflow states. 470 h (74 %) of that was waiting on Ben: 294 h in Needs input and 176 h in In review. Agents worked 57 h in Implementing and 15 h in Planning. The gate step that runs checks and waits on CI took 60 h. The workflow does not get stuck because agents are slow. It gets stuck because too much reaches a human, and once it reaches a human nothing moves it on.

Top 5 findings

  1. Waiting on a human dominates. Needs input has a median wait of 12.7 min but a p90 of 7.3 h, with 101 re-entries across 81 tickets. Nothing escalates or times out a question in the live workflow (I-1).
  2. The fixes are built but not switched on. ADR-0037's watch, notify policy, handoff and instructions are in code, and conductor.v6.json was committed on 2026-11-09. The live workflow is still v5 (I-10).
  3. The PR gate has run checks that did not test the code. Until 2026-11-06 every PR ran npm run build and npm test on a pnpm and Cargo repo: 662 runs, with "Tests pass" failing 56 times (17 %). Rust and Windows breakage passed locally and failed in CI, three rounds in a row on 08e318fb. The new pnpm repo checks run the full suite twice: once in conductor's checkout and again in GitHub CI, docs-only diffs included (I-3, I-4).
  4. Hand-offs double as questions. Agents put questions inside "PR ready for review" summaries ("could you send me that output…", "Is the 4-line case OK?"), so Ben has to read a review hand-off to find out it is really a blocker (I-2).
  5. Simple things bounce to Ben. 67 questions came up in 30 days, 35 of them during planning. Some are scope questions the prompt already tells the planner not to ask: 515b97b4 waited 970 min to be told an existing feature covered the ticket. Environment problems (no node_modules, corepack, Docker pools) show up in 27 of the 64 analysed sessions (I-6, I-7).

Top 5 proposals by RICE

  1. R1 · Save conductor v6 live: mergeability watch on In review, a 2 h escalation on Needs input, hand-off vs question, and the notify policy. Score 680.
  2. R14 · Alert when a main deploy fails: deploys rolled back silently for about three days. Score 210.
  3. R2 · Install dependencies in the agent's worktree before it starts, reusing the repo checks' setup. Score 102.
  4. R3 · Diff-aware gate with one source of truth: conductor runs fast, affected-only checks and GitHub CI stays the full gate. Docs-only diffs skip the tests. Score 95.
  5. R8 · Requirements reviewer on personal PR hand-offs: the ADR-0009 reviewer already exists and only the work kind uses it. Score 85.

On the ticket's main question, conductor-owned AI states: an "answerer" pass (R5a, score 54) is the cheap first step. A full triage state type (R5b, score 27) is worth it once R1–R4 have removed the noise it would otherwise spend its time triaging. See §4.4.

3 · Conductor's workflow engine vs n8n

3.1 · Two different models

conductor: a durable per-ticket state machine

  • A workflow is versioned JSON. The engine is the pure function apply(state, event) → (state', effects). Each event is persisted in one transaction with its outbox commands.
  • State types: agent (Claude Code on a daemon), command (a shell step on a daemon, which moves on its exit code), event (waits on named events or a timeout), connector (an orchestrator action), human (a board card with buttons), and terminal.
  • Transitions only on outcomes: an agent names a transition through complete_state, and free text is never interpreted. Transitions can carry requires, which runs in order: a held phase (concurrency), checks in a fresh checkout, an AI requirements reviewer, actions (open_pr), and polled external conditions (pr_checks_green, pr_mergeable, cmd…). Their on_unmet loop is counted and bounded.
  • Every loop is bounded and every failure ends at a human state. Since ADR-0037 a state can watch its conditions while a ticket waits in it.
  • A ticket is one long-lived execution: days long, with a git worktree on a specific machine, a resumable Claude conversation, a board column, and analytics.

n8n: a node graph that executes once per trigger

  • A workflow is a graph of nodes. An execution starts from a trigger (webhook, form, schedule, app event) and passes items (JSON) from node to node.
  • Branching uses IF, Switch and Merge on any expression over the data. Sub-workflows provide reuse.
  • Long pauses use the Wait node, which resumes on a time, on a per-execution $execution.resumeUrl webhook, or on a form submission. Human approval uses Send and Wait for Response in Slack, Teams, Gmail, Telegram or Chat, with a "limit wait time" fallback.
  • Errors are handled with per-node Retry On Fail and On Error (stop, continue, or a dedicated error output) and a workflow-level error workflow.
  • The AI Agent node calls tools, and individual tools can be gated by human review. n8n scales out with queue mode: Redis plus workers.

3.3 · What the mock had to fake

Rebuilding v5 in n8n mostly means re-implementing things conductor already does:

  • Per-ticket durable state. An n8n execution holds its state only while it lives. Retry counters, the Claude session id, the plan and the PR URL would need a datastore (n8n Data Tables or Postgres), and every agent node would read and write it.
  • "Back to the agent that asked." $return_to needs a lookup and a Switch per caller. In the mock, the Needs input reply always goes to the Planner, which is wrong for implementing questions.
  • Machine placement and worktrees. One SSH credential is hard-wired. Routing by capability and repo exclusivity (ADR-0013), concurrency holds and a lost machine would each be hand-built.
  • The gate step. Checks pinned to a commit, a fresh checkout, setup triage ("is it the branch or the base?"), then open_pr with the exact SHA. n8n has the pieces but none of the guarantees.
  • Bounded loops. n8n will happily run an unbounded loop. Every IF counter in the mock is hand-written, and nothing validates that one exists.
  • A board. n8n has an executions list, not a kanban of "what needs me".

3.5 · Possible in n8n, not in ours

  • Fan-out and join. Run a reviewer, the Windows leg and a docs check at the same time, then Merge. Conductor's single-state session can't express "these three in parallel, continue when all report". It approximates it inside one gate step by running checks in sequence.
  • A timeout that chooses a branch. Send-and-wait with a time limit resumes on its own and takes a default. Conductor's timeouts always land on a human; v6's watch can escalate but never decide.
  • Answering where the human already is. Approve or reply inside Slack or Teams, with the approver restricted and recorded.
  • Event-driven resumption. A GitHub check_run or pull_request webhook resumes the flow. Conductor polls every 1–15 min, which is fine, but slower and harder to reason about.
  • Calling a reusable sub-flow, for example one "fix-CI" routine used by both PR transitions and the watch.
  • A dedicated error flow that runs on any failure: page someone, open a ticket, try an automatic remedy.
  • Replay with pinned data. Re-run one node of a past execution with its recorded input while editing the workflow.

3.6 · Easier in n8n than in ours

  • Adding a small deterministic step. In n8n you drop in an HTTP or Code node. In conductor you write a cmd condition or a command state that must run on a daemon, or a code change for a new connector action.
  • Routing on a value. "If the diff only touches docs/, skip the tests" is one IF node. In conductor it needs a new condition type or a check that exits 0 early.
  • Trying a change. n8n runs a partial execution on pinned data. A conductor workflow edit is a new version that only shows its effect on the next real tickets.
  • Integrations. Jira, Slack, Linear and email are a credential and a node away. Conductor's are milestone M5.

3.7 · What ours does that n8n doesn't (and why we shouldn't move)

  • One execution per ticket for days, with a worktree, a resumable conversation and machine affinity. This is the hard part of agentic coding, and n8n has no model for it.
  • Validated guarantees: loops are bounded, every failure path ends at a human, and state changes are exactly-once with idempotent side effects. n8n leaves all of these to the author.
  • Gate steps pinned to a commit (check, then review, then open_pr on the same SHA) and setup triage.
  • The board, and analytics that know what a "rework loop" or a "question" is.
Conclusion: borrow n8n's primitives and keep conductor's model. The gaps that matter for the problems in §4 are a default-on-timeout for questions, routing on cheap facts (diff paths), parallel gate legs, answering in Slack, and an error/triage flow that runs before a human is paged.

4.2 · Are checks run when they make no sense?

Yes, in three ways.

  1. Wrong commands (until 2026-11-06). The workflow default ran npm run build and npm test on every repo. On this pnpm and Cargo repo, "Build passes" ran 334 times (6 failures) and "Tests pass" ran 328 times (56 failures, 17 %). They never covered Rust: 08e318fb (MR-T12) passed them three times while the Windows daemon-rust leg failed after each hand-off. The analyst flagged this mismatch 31 times (19 + 12 sessions). The repo checks override that has existed since 2026-11-06 fixed the commands: Typecheck, Lint, Tests, Build and "Merges cleanly", with 4 failures in 137 runs.
  2. The same gate runs twice. The override runs pnpm typecheck, pnpm lint, the full pnpm test (30 min timeout) and pnpm build in a fresh checkout. Then pr_checks_green waits on GitHub's gates job, which runs scripts/ci.sh, the same suite plus Rust and e2e, on the same commit. Conductor's run is the less selective one: it doesn't set CONDUCTOR_CI_TIERED=1, so a PR runs every test tier locally while CI runs only the tiers the diff reaches.
  3. The gate doesn't look at the diff. This ticket only adds two files under docs/reports/, which no gate lints or tests, and it will still pay the full local gate and the full CI wait. The gate step averages 10.5 min a pass. About 142 of 349 passes did not reach review, roughly 25 h of gate time spent on attempts that bounced (an estimate: median × non-landing passes).

4.4 · Should conductor own states run by dedicated AI agents?

Yes, as a filter in front of Ben. The data suggests three roles, from cheapest to most ambitious:

  1. Reviewer on hand-off (exists): the ADR-0009 reviewer, a fresh read-only session that judges a checklist against the diff, already runs on work-kind PR transitions. Personal PRs, which are every ticket on this repo, skip it, and 25 % of reviews end in request_changes.
  2. Answerer (new, small): before an agent_question opens on the board, a fresh session with read access to the repo, the ADRs, the ticket, earlier answers on the ticket and gh tries to answer it. If it is confident, the answer goes back to the asking agent marked "answered by conductor" and Ben is told, not asked. If not, the question goes to Ben with the answerer's findings attached. In n8n terms this is an AI Agent node plus a Switch in front of Send-and-Wait.
  3. Triage (new state type, larger): on check_failed, condition_unmet, retries_exhausted and setup failures it decides between send back with a precise instruction, retry or rerun a flaky job, fix the environment (a command), or escalate with a diagnosis. This is n8n's error workflow made into an AI agent.

The invariants still hold: the AI only picks among declared transitions, each loop through it is counted, and it ends at a human. The risk is an AI confidently answering a question only Ben can answer, such as product intent or money. Two mitigations: the answerer may only answer from cited sources, and certain transition kinds (plan_needs_approval, needs_approval_to_message) are never routed to it.

4.5 · Other insights

  • Budgets are decorative. v5 declares $5 and 240 min, yet there were 0 budget_exceeded moves across 2,071 moves. The sampled tickets spent $6.43 (0ca2aa8b), $8.29 (d0f8e9aa) and $21.04 (4568a293, a navigation cleanup). Nothing emits budget.exceeded (TD-015), and the daemon ignores max_budget_usd (TD-022).
  • Deploys failed silently. ade0e150's implementer found that every deploy of main from 2026-11-06 16:03 UTC until its fix had failed and rolled back, because .dockerignore dropped workflow JSON that tests import. No one was told.
  • Scope creep in implementing. The analyst reported unclear_requirements (15) and other (14) in implementing. 7811f19d grew from a quarantine script into Rust daemon changes, CI, a runbook and design docs.
  • Agents improvise their edit tooling. Python str.replace edits that silently didn't apply (a68f92b5, 7811f19d) account for 19 tool_error frictions.
  • Planning has no shell. planning.tools = ["read"], so the planner can't run git log or gh, and some sessions waste a turn trying to (515b97b4).
  • Analytics coverage. The analyst sees 42 % of sessions. 44 % of moves predate cause recording, so the loop tables will only become reliable from here on.
  • Plan over-escalation was already fixed. The 2026-11-04 analysis behind 6b386e59 found 16 plan approvals in 37 tickets, about half answered with a canned "Plan approved". v5 and the CLAUDE.md change made additive schema changes routine. Since then only 4 tickets have stayed in plan_review (27 plan_needs_approval records over the window, mostly from before). The planning waits that remain come from scope_changed and needs_product_context: the same fix, applied to those two.

7.2 · Workflow edits (no engine change)

R1 · Save conductor v6 live

The file is ready (docs/design/workflows/conductor.v6.json, validated by conductor.v6.test.ts). Ben runs save_workflow; it's admin-only, so an agent can't do it. It brings:

"in_review":  { "watch": { "poll": "2m", "conditions": [{ "type": "pr_mergeable" }],
                 "on_broken": { "goto": "implementing", "instruction": "$instructions.resync_main",
                                "return_to": "$self", "retries": 3, "else": "needs_input" } } },
"needs_input": { "watch": { "poll": "5m", "conditions": [{ "type": "age_below", "max": "2h" }],
                 "on_broken": { "notify": "escalate" } } },
"notify": { "default": "once", "engine_moves": "never", "coalesce": "15m" }
// PR-ready transitions: "question": true  →  "handoff": true

Risk: low. Every primitive is off until the definition sets it, and the T9 ticket diffed v5 against the draft. ADR: none (ADR-0037).

R8 · Reviewer on personal PR hand-offs

Copy the work transition's requires.review onto personal_pr_ready_for_review, with items taken from the ticket template:

"requires": { "review": { "items": [
  "Every functional requirement in the ticket body is met by the diff, or the summary says why not.",
  "The diff changes nothing the ticket's Out of scope section excludes; extras are proposed tickets.",
  "The summary does not ask Ben a question; a question would have used ask_user."
] }, ... }

Risk: about 1–3 min and some cost per hand-off. It could fail reasonable PRs, but on_unmet gives the agent the verdict and the loop is already bounded. ADR: none.

R7 · Planner policy

  • Change the scope_changed and needs_product_context when text to: "Only when no reasonable default exists. Otherwise plan your recommended option, list it under 'Assumptions' at the top of the plan, and propose the alternative as a follow-up ticket."
  • Add to the plan template: "Existing mechanisms checked: …" (a grep for similar concepts before proposing a new table or tool).

7.3 · Tooling

R2 · Dependencies before the agent starts

When the daemon creates a ticket worktree, it runs the repo's repo-check setup there (for this repo: pnpm install --frozen-lockfile and the main fetch) before start_session. A failure is reported as a setup failure with the same "whose problem is it" triage, not as agent rework. Also set COREPACK_ENABLE_DOWNLOAD_PROMPT=0 in the agent environment. Schema: optionally a repo_checks.worktree_setup column when it should differ from the check setup.

R3 · Diff-aware gate; CI is the full gate

  • Repo checks for this repo become: "Merges cleanly", pnpm typecheck, pnpm lint, and CONDUCTOR_CI_TIERED=1 pnpm test (affected tiers only). pnpm build is dropped because CI builds. pr_checks_green remains the authority.
  • Engine: an optional paths filter on a check, so it runs only when the diff from the merge base touches those globs: 
    { "name": "Tests", "cmd": "CONDUCTOR_CI_TIERED=1 pnpm test", "paths": ["packages/**", "crates/**", "e2e/**", "scripts/**"] }
    A docs-only diff then runs only "Merges cleanly". This is n8n's IF node, kept declarative.
  • For Rust, add cargo clippy and nextest checks with paths: ["crates/**", "Cargo.*"]. The Windows leg stays CI-only and is covered by pr_checks_green.

R4 · Let the agent run the gate itself

Add an MCP tool run_gate for worker agents. It runs the transition's effective checks (repo override included) in a fresh checkout of the agent's HEAD on the same daemon, and returns pass or fail per check with output tails. The implementing prompt then says: "Run run_gate until it passes before choosing a PR-ready transition." This removes the guesswork of "which command is the gate" (tool_error 19, flaky_check 14) and moves failures into the agent's own loop, where they cost no round trip. Risk: it uses more build slots; it shares the existing semaphore.

R14 · Deploy-failure alert

deploy/gradyserver/deploy.sh's rollback path calls conductor's API to push a notification and open a ticket on this repo ("Deploy of <sha> failed: <step>"). Alternatively, a recurring schedule (ADR-0032) checks the deployed SHA against origin/main every hour.

R9 · Enforce budgets

Pay TD-015 (emit budget.exceeded from accumulated spend and wall time) and TD-022 (pass --max-budget-usd). First set realistic numbers from the data, about $15 and 240 min: the declared $5 would stop many normal tickets today.

R13 · Signals

  • A per-machine health finding when stops or check failures exceed 2× the account median over 7 days (ea6d442e).
  • Analyse every finished session, not 42 %; at Haiku prices this is cents.
  • Add an "auto-answer rate" metric once R5a lands.

7.4 · Engine capabilities (inspired by n8n)

R5a · Answerer pass n8n: AI Agent → Switch → Send-and-wait

A workflow-level answerer block, reusing ADR-0009's reviewer machinery (fresh session, read-only tools, dontAsk):

"answerer": {
  "applies_to": ["ask_user", "scope_changed", "needs_product_context"],   // never plan_needs_approval
  "model": "sonnet",
  "sources": ["repo", "adr", "ticket", "prior_answers", "gh_read"],
  "min_confidence": "high"
}

Its verdict is {answer, confidence, citations[]}. With high confidence and at least one citation, the answer goes to the asker as input.provided with answered_by: conductor, and Ben gets a push he can veto ("Overrule" re-opens the question). Otherwise the question opens as today, with the answerer's notes attached. Needs an ADR: it changes who may answer a question (06-human-input).

R6 · Default on timeout n8n: send-and-wait "Limit wait time"

"ask_user": { "goto": "needs_input", "default": { "after": "2h", "answer": "$recommended" } }

The agent's complete_state already carries a recommended answer (the prompt requires one). After after with no human reply, the engine delivers it as the answer, records cause: default_taken and notifies. This is bounded and visible, and Ben can still overrule it. Needs an ADR: it is the first engine move that answers on a human's behalf.

R5b · triage state type n8n: error workflow

"triage": { "type": "agent", "role": "triage", "tools": ["read", "bash:readonly", "gh_read"],
  "on": {
    "send_back":  { "goto": "$return_to", "attach": "output", "retries": 2, "else": "needs_input" },
    "rerun":      { "goto": "$gate", "retries": 1, "else": "needs_input" },
    "fix_env":    { "goto": "env_fix", "retries": 1, "else": "needs_input" },
    "escalate":   { "goto": "needs_input", "question": true }
}}
// and on the PR gate:  "on_unmet": { "goto": "triage", ... }

Engine changes: an agent state may be an on_unmet.goto target that resolves $return_to (today only human states use it), and a $gate ref meaning "retry the move that failed". The verdict is still a declared transition, so the validator's loop analysis applies unchanged. Needs an ADR.

R10 · Parallel legs n8n: fan-out + Merge

Inside a move step: requires.parallel: [[checks…], [review], [cmd: windows leg]]. The legs run at once on suitable machines, all must pass, and the first failure reports. This is far cheaper than general fork/join states, which would break "one state per session". Needs an ADR.

R11, R12, R15–R17

  • R11 GitHub webhooks set watch_deadline = now or state_deadline = now, like ADR-0037's internal nudge. Polling remains the backstop.
  • R12 Slack answering (U-007): send-and-wait style buttons for $return_to answers and plan approval.
  • R15 Reusable fragments: named requires blocks referenced as $gates.pr, the way $instructions works.
  • R16 retry_after with exponential delay on setup and action_failed before counting a retry.
  • R17 simulate_workflow(version, ticket_ids): replay recorded event streams through apply() against a draft version and diff the routes. apply is pure, so this is n8n's pinned-data debugging, but for a whole process.
